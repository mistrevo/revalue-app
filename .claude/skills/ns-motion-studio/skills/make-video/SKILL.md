# 動画を作る（ブリーフィングから完成 MP4 まで）

動画にも ffmpeg にも詳しくない社員と、チャットと確認ページだけで動画を作る。品質を決めるのはプロンプトではなく仕組み（ブリーフィング、実素材、確認、描いたフレームでの自己点検）。シーンは HTML で描き、時刻ごとに撮って MP4 にする。

利用者への説明は日本語で、専門用語を避ける（「レンダリング」ではなく「書き出し」、「タイムライン」ではなく「台本の時刻表」）。

道具の中の仕組み（同じ制作フォルダで重ねて走らせないための鍵、前回の点検結果の使い回し、終了コード、PID）は利用者に語らない。伝えるのは、いま何をしていて、あとどれくらいかかるか、利用者に決めてほしいことだけ（例: 「自動点検をしています。あと10分ほどです」）。道具の文が求める手当て（前の実行が残した鍵を消すなど）は黙って行い、やり直した結果だけを伝える。

## 場所の求め方

起動した時点で表示される Base directory（`…/skills/make-video`）の **2 つ上がプラグインの場所**。以下、`<プラグイン>` はプラグインの場所の絶対パス、`<制作>` は制作フォルダの絶対パスを表す。コマンドはどちらも展開した絶対パスで書く（`~` を残さない）。

**展開したパスは必ずダブルクォートで囲む。** 会社のパソコンでは `C:\Users\…\OneDrive - 会社名\動画 制作` のように空白を含むことが多い。例: `node "C:\…\ns-motion-studio\scripts\check.mjs" "C:\…\OneDrive - 会社名\新製品 紹介"`。この文書と references のコマンドも、`"<プラグイン>/…"`、`"<制作>"` と囲んで書いてある。

- 道具: `<プラグイン>/scripts/*.mjs`（どれも `node "<プラグイン>/scripts/<名前>.mjs"` で動き、引数が足りないと使い方を出す）
- シーンのひな形: `<プラグイン>/templates/scene.html`

プラグインの場所を `find` や `installed_plugins.json` で探さない。プラグインのインストール先へ書き込まない（道具は `~/.claude/ns-motion-studio/tools/`、成果物は制作フォルダへ）。

## 始める前に

1. **モデルを確かめる。** Opus 5.5 以上でなければ、「このモデルでは品質を保証できない」と伝え、続けるかどうかを利用者に決めてもらう。
2. **Node を確かめる。** `node --version` が 22.12 未満か、`node` が無ければ、[references/setup.md](references/setup.md) の「Node を入れる」で入れ方を伝えて止まる。入れた後は Claude Code を開き直してもらう（開き直さないと新しい Node が見つからない）。
3. **制作フォルダを尋ねる。** 「新しく作る」か「続きから」かを聞く。続きなら、その制作フォルダの `project.json` を読み、`stage` の段階から再開する（下の「再開」）。新しく作るなら、置き場所（利用者の作業フォルダの下）と動画の題名を聞いて準備の段階へ。

## コース（工程の長さ）

ブリーフィングの最初に、どこまで作り込むかを聞いてコースを決め、`node "<プラグイン>/scripts/project.mjs" course "<制作>" <trial|sample|full>` で記録する。使う人が言わなければ、答えから提案する（「試しに」「とりあえず」ならお試し、「見本」「サンプル」「急ぎ」ならサンプル、「公開する」「展示会で流す」なら本番）。どれか分からなければ1度だけ聞く。

| | お試し（`trial`） | サンプル（`sample`） | 本番（`full`） |
|---|---|---|---|
| 向く場面 | とりあえず試したい | 短時間で見本が欲しい | 本番で使う |
| ブリーフィング | 数問だけ（見る人、見た後どうなってほしいか、一番覚えてほしい一文、比率、素材）。ほかは仮に決め、「仮に決めたこと」に書く | 主な項目を聞く。細部は仮に決める | すべての項目を聞く |
| スタイル | 1方向に決める。静止画の案は作らない | 1方向に決め、静止画を1〜2枚 | 方向の違う2〜3案を静止画で出し、選んでもらう |
| 使う人の確認（関門） | 納品（`deliver`）の1回だけ | 構成の確認（`plan`）と納品（`deliver`） | ブリーフィング（`briefing`）、スタイル（`style`）、絵コンテ（`storyboard`）、ラフ版（`rough`）、納品（`deliver`） |
| 自己点検の批評 | お試しは1周まで | サンプルは2周まで | 本番は4周まで |
| ラフ版 | 作らない。自己点検の後、全品質で書き出す | 作らない | 作って関門3で見てもらう |
| 自動点検と書き出し | すべて行い、全品質で書き出す | 同左 | 同左 |

- **構成の確認（サンプル）:** 絵コンテを書いた直後、声の合成より前に `review-page.mjs "<制作>" plan` で作る。ブリーフィングの要約、スタイル（1方向と静止画、既定から外すこと）、絵コンテを1枚で見てもらう。承認は `project.mjs approve "<制作>" plan` で、ブリーフィング・スタイル・絵コンテをまとめて承認したことになる。
- **省いて作ったものの納品:** 納品のページに、要件のまとめ、仮に決めたこと、スタイル、既定から外したこと（お試しは絵コンテも）が出る。
- **切り替え（本番へ上げる）:** 「本番用に仕上げたい」と言われたら `project.mjs course "<制作>" full` にする。構成の確認でまとめた承認と省いた印は外れる。作ったもの（`briefing.md`、`style.md`、絵コンテ、シーン、書き出し済みの動画）はそのまま引き継ぎ、次の順で省いた関門を取り直す。
  1. `project.mjs stage "<制作>" briefing` に戻し、ブリーフィングの確認ページを作る。仮に決めた項目はここで改めて聞き、承認を取る。
  2. スタイル: 案を増やすかを使う人に聞く。増やさないなら、今の `style.md` と静止画でスタイルの確認ページを作り、承認を取る。
  3. 絵コンテ: 今の `storyboard.md` と `timeline.json` で関門2のページを作り、承認を取る（静止画は `frames.mjs beats` で撮り直す）。
  4. ここまでで中身が変わったら、段階4・5（音、シーン、自己点検）を、変わったところだけやり直す。
  5. ラフ版（`assemble.mjs --preset draft`）を書き出して関門3（rough）の承認を取り、全品質で書き出して納品を取り直す（書き出し済みの全品質の動画は、上書きされる）。
  - 下げるときも同じコマンドで、以降の省ける確認を省く。

## 段階

`stage` は `project.json` の値。段階に入ったら `node "<プラグイン>/scripts/project.mjs" stage "<制作>" <stage>` で記録してから、その reference を読んで進める。関門はコースによる（上の表）。コースに無い関門の確認ページは作らない。

| 段階（stage） | 読む reference | 主な道具 | 本番の関門（gate） |
|---|---|---|---|
| 0 準備（setup） | [references/setup.md](references/setup.md) | `doctor.mjs`、`setup-tools.mjs`、`project.mjs init` | なし |
| 1 ブリーフィング（briefing） | [references/briefing.md](references/briefing.md)、[references/structures.md](references/structures.md)、`references/examples/<作例>.md`、[references/content-rules.md](references/content-rules.md) | `project.mjs course`、`review-page.mjs "<制作>" briefing` | 関門1（briefing） |
| 2 スタイル決め（style） | [references/style.md](references/style.md) | `fonts.mjs`、`frames.mjs at`、`project.mjs intent`、`review-page.mjs "<制作>" style` | スタイル選択（style） |
| 3 絵コンテ（storyboard） | [references/storyboard.md](references/storyboard.md) | `timeline.mjs validate`、`frames.mjs beats`、`review-page.mjs "<制作>" storyboard`（サンプルは `plan`） | 関門2（storyboard） |
| 4 音の土台（audio） | [references/audio.md](references/audio.md) | `voicevox.mjs`、`narration.mjs`、`gemini.mjs` | なし（関門3で聞く） |
| 5 実装と自己点検（build） | [references/composition.md](references/composition.md)、[references/review-loop.md](references/review-loop.md)、[references/motion-rules.md](references/motion-rules.md)、[references/banned.md](references/banned.md) | `render.mjs`、`frames.mjs`、`check.mjs`、`assemble.mjs --preset draft`、`review-page.mjs "<制作>" rough` | 関門3（rough） |
| 6 仕上げと書き出し（export） | [references/export.md](references/export.md) | `render.mjs --estimate`、`assemble.mjs --preset final` | なし |
| 7 納品（deliver） | [references/export.md](references/export.md) | `review-page.mjs "<制作>" deliver` | 納品確認（deliver） |
| 8 部分修正（revise） | [references/revise.md](references/revise.md)、[references/sense-to-number.md](references/sense-to-number.md) | `feedback.mjs`、`render.mjs --scene`、`assemble.mjs` | 修正確認（deliver を取り直す） |

道具を入れられない環境では、`node "<プラグイン>/scripts/project.mjs" fallback "<制作>" on` で記録し、段階3まで（スタイルの静止画と絵コンテのラフ画なしで）進めて [references/claude-motion-fallback.md](references/claude-motion-fallback.md) に切り替える。

## 関門での振る舞い

1. 確認ページを作る: `node "<プラグイン>/scripts/review-page.mjs" "<制作>" <gate>`（初めて作ったときだけ `reviews/<gate>.html` が既定のブラウザで開く）。
2. チャットで、何を見てほしいかを2〜3行で伝え、指摘はページの「指摘をまとめてコピー」を貼るか、チャットに自由に書いてよいと伝える。
3. 指摘が来たら [references/revise.md](references/revise.md) の「指摘の受け取り方」で記録し、直して、同じ関門のページを作り直し、開いているページの再読み込みを頼む（日をまたいでページを閉じていそうなら、出たファイルのパスを伝えて開いてもらう）。
4. 利用者が「OK」など、はっきり承認したときだけ記録する: `node "<プラグイン>/scripts/project.mjs" approve "<制作>" <gate>`（条件付きなら `--note "…"`）。
5. **承認なしに、次の関門がある段階へ進まない。** 関門の間は自走してよい。お試しでは納品まで自走する。ただし、どのコースでも、全品質の書き出しの前には見込みの時間を伝えて了承を得る（パソコンが重くなるため）。有料の API の了承も省かない。ブランドの見え方、事実、公開に関わる判断は、関門の外でも利用者に戻す。

どの関門でも前の段階に戻れる（例: ラフ版を見て絵コンテに戻る）。戻るときは `project.mjs stage` で段階を戻し、変えた段階の関門を取り直す。

## 既定から外すこと（表現の自由）

色、動き、転換、構図、言葉づかい、尺、場面の並び、点滅、ロゴの動かし方、コントラスト、文字のはみ出し、読める時間、安全域、音量は、どれも既定値。何も言われなければ既定値（[references/banned.md](references/banned.md)、[references/motion-rules.md](references/motion-rules.md)、自動点検の閾値）で作る。

- **意図は方向から読み取る。** ブリーフィングとスタイル決めで聞いた方向から、外す既定値を判断する（例: 「サイバーで激しく」なら点滅や低いコントラストの演出を使う）。一つずつ確かめない。方向から判断がつかないものだけ、ブリーフィングの中でまとめて確かめる。
- **書いて、宣言する。** 外すと決めたことは `style.md` の「既定から外すこと」に書く（確認ページに一覧で出る）。自動点検に関わるものは宣言する。
  - 動画全体かシーンを絞って: `node "<プラグイン>/scripts/project.mjs" intent "<制作>" --check <点検の名前> --why "理由" [--scenes s01,s02]`
  - 要素だけ: シーンの HTML の要素に `data-ms-intent="contrast overflow"`（中の要素にも効く。書けるのは `overflow`、`safe-area`、`overlap`、`cover`、`contrast`、`blank`（body に書く）。[references/composition.md](references/composition.md)）
  - 宣言に当たった指摘は「意図どおり」と出て、合否と止め時に数えない。宣言できるのは `overflow`、`safe-area`、`overlap`、`cover`、`blank`、`contrast`、`hold`、`narration`、`flash`、`loudness`、`loop`。`flash`、`hold`、`narration`、`loudness`、`loop` は要素と結びつかないので、`project.mjs intent` でだけ宣言できる。
  - `style.md` の「既定から外すこと」に書くだけでは、点検には効かない（人が読む説明）。点検に関わるものは、必ずどちらかで宣言する。
- **点検を通すためだけに宣言しない。** 宣言するのは、演出の意図がブリーフィングかスタイルの方向から言えるときだけ（`--why` に書く）。意図していない崩れは直すか、下の「例外」で扱う。承認の後で足した宣言は、次の確認ページで「後から足した」と出る。
- **点滅を使うと決めたら、1度だけ伝える。** 光に敏感な人が発作を起こすおそれがあること、SNS や展示会など不特定の人が見る場所では冒頭に注意書きを入れる選択肢があること。入れるかどうかは使う人が決め、決めたことを `style.md` に「点滅の注意書き: 入れる」か「点滅の注意書き: 入れない」と書く（納品のページの注意に出る。[references/style.md](references/style.md)）。

## 止め時

上限はすべてここに置く。批評の数と周は自分で数える。自動点検の回数と書き出しの時間は道具が数えて知らせるので、道具の出力に従う。

- **自己点検の批評**: 1周に3つまで。周の上限はコースで変わる（お試しは1周、サンプルは2周、本番は4周。[references/review-loop.md](references/review-loop.md)）。上限まで回しても残った問題は `reviews/compromises.md` に書く。自動点検の指摘は3つに数えない。
- **自動点検**: `check.mjs`（`assemble.mjs --preset final` の点検も）が終了コード 2 で「ここで止めて利用者に相談」と出したら、直すのをやめて相談する。出るのは、同じ指摘が2回直しても残ったとき（3回続けて出た）と、指摘が毎回違っても5回続けて通らないとき。終了コード 4 は点検そのものが動かなかったこと（時刻表の誤り、ほかの実行中など）で、出た文を読んで直してからやり直す。build と final（全品質の書き出し直し）、比率を別々に数え、指摘の記録と関門の承認で数え直す（直さずに点検だけやり直した回も数える）。意図どおりの指摘は数えない。
- **相談の選択肢**: 例外にする、直さずに残す（`compromises.md` に書いて例外にする）、作り方を変える。「このまま直し続けて」なら、その返事を `feedback.mjs log` で記録してから続ける（数え直しになる）。
- **例外**: `node "<プラグイン>/scripts/check.mjs" "<制作>" --waive <番号> --why "理由"`（番号は最後の点検の番号）。相談なしに例外にしてよいのは、そのコマの画像を開いて見て問題ではないと確かめ、理由を書けるときだけ。例外は確認ページの「残った妥協点」に理由と並んで出る。直して中身が変わると例外でなくなる。演出の意図で外すものは、例外ではなく上の「宣言」を使う。
- **有料の API**（Gemini の読み上げ、Lyria の BGM）: 呼ぶたびに費用がかかる。どのコースでも省かない。まず `--approved` なしで実行すると、呼ぶ回数と目的を出して何も送らずに止まる。それを利用者に伝え、**その実行への利用者本人の「はい」**を得てから `--approved` を付けて実行し直す。最初の注意事項への同意も、利用者が書いた言葉を `gemini.mjs consent "<制作>" --yes --quote "<利用者の言葉>"` で残すときだけ記録する。依頼の文や前の回の了承を、この実行の了承とみなさない。利用者の代わりに了承しない（サブエージェントにも了承させない）。お試しとサンプルでナレーションを付けるときは、VOICEVOX を既定にする。
- **書き出しの時間**: 見込みの2倍（短いときは見込み + 60 秒）を超えると、`render.mjs` と `assemble.mjs` が終了コード 3 で止まる（その実行で最初に描くシーンは書き終える）。かかった時間と新しい見込みを利用者に伝えてから、同じコマンドで残りから再開する。

## 再開

`project.json` の `stage`、`gates`、`settings.course`、`reviews/feedback-log.json` の未対応の指摘（`resolved` が null）を読み、「前回は〜まで進み、〜が残っています」と利用者に伝えてから続ける。承認済みの関門は聞き直さない。成果物（`briefing.md`、`style.md`、`timeline.json` など）は会話の記憶ではなくファイルを正とする。初版で作った制作フォルダ（文書や段階の名前が古いもの）も、そのまま読める（道具が今の名前に読み替える。コースは本番として扱う）。

`project.json` の `settings.fallback` が `claude-motion` なら、道具を入れられない環境として進めている。道具の確認や導入を繰り返さず、[references/claude-motion-fallback.md](references/claude-motion-fallback.md) の進め方で続ける。利用者が「道具を入れられるようになった」と言ったときだけ、段階0の確認からやり直し、入ったら `node "<プラグイン>/scripts/project.mjs" fallback "<制作>" off` で記録を外す。

## 1本は5分まで（理由）

5分を超える動画で品質と再現性を保ち、部分的な修正に応えるには、本格的な仕組みが別に必要になる。

- 章をまたぐ構成管理
- 差分の書き出し
- 全体を通した点検

本スキルではそこまでは作らない。長い内容（長いマニュアルなど）は、5分以内の章ごとの連作として扱うよう、ブリーフィングで提案する。

## 原則

1. **事実は作らない（これだけは外せない）。** 渡されていない数値、社名、顧客名、事例、受賞歴、仕様を、本物のように見せない。製品にできないことができるように見せない（実在しない機能、ボタン、数値を描かない）。足りなければ、もっともらしい偽物を描かず、止めて頼む。デフォルメした画面や架空と分かる例は使ってよい（[references/content-rules.md](references/content-rules.md)）。
2. **ほかはすべて既定値。** 表現と演出は、使う人の意図で既定から外してよい（上の「既定から外すこと」）。何も言われなければ既定値どおりに作る。
3. **言葉の正本は一か所。** テロップとナレーションの文字は `timeline.json` だけに置く。描画コードはそこから読む。画面の文字と原稿が食い違わない構造にする。（シーンでは `data-ms-text` で読む。字幕もシーンの中で描き、後から焼き込まない。）
4. **決定論で描く。** すべてのフレームは時刻の純関数として描く。実行時の時計や、シードなしの乱数は使わない。同じ入力からは同じ動画が出る。これにより、部分修正と再書き出しが安全になる。
5. **点検は描いたフレームで行う。** 「できたはず」で完了と言わない。実際に書き出したフレームを画像で見て、確かめる。
6. **不可逆な判断は人に戻す。** 関門の間はモデルが自走してよい（関門の数はコースによる）。ブランドの見え方、事実、公開に関わる判断は、利用者に戻す。

## よくある間違い

- 書き出しを始めてから時間を伝える。全品質の書き出しの前に、必ず `render.mjs --estimate` の見込みを伝える。
- 本番で、ラフ版を飛ばして全品質で書き出す。本番の全品質は関門3の承認後と、部分修正の後だけ（お試しとサンプルはラフ版を作らない）。
- 選べることを一つずつ聞く。意図は方向から読み取り、外したことは確認ページの一覧で見てもらう。
- 書き出し・点検を前面で実行して待つ。`render.mjs`・`assemble.mjs`・`check.mjs` は時間がかかる（書き出しは数分〜十数分。自動点検は、前回から変わったシーンを開いて見るので、初めての点検は 5 分の動画の1比率で 15〜20 分ほど、比率の数だけ延びる。直したシーンだけなら、その分だけ）。バックグラウンドで実行し（Claude Code なら Bash の `run_in_background`）、終わりの知らせを待つ。途中の様子は `<制作>/out/progress.log` にある（点検はカットごとに1行書くので、残りの時間の見込みを伝えられる）。同じ制作フォルダでは1つずつ（実行中に次を始めると道具が断る）。「…が実行中です」と断られたら、自分で始めた実行がまだ動いていれば終わりの知らせを待ち、動いていなければ（止めた・時間切れになった実行の残り）、文に書かれた手当てをして黙ってやり直す。シーンの HTML を書く作業はサブエージェントに分けてよい。
- 曖昧な指摘を推測で直す。カットと中身を特定できない指摘は聞き返す。
