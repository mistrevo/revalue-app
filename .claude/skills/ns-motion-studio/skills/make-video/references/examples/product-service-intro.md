# 作例: 製品・サービス紹介

こういう依頼なら、こう組むとよい一例。決まりではないので、使う人の意図に合わせて変えてよい。

## どんな依頼の例か

製品やサービスが「何で、誰の、どんな困りごとを、どう解決するか」を理解してもらいたい。ローンチより落ち着いた調子で、検討中の人が判断に使える情報を順に渡す。営業の場、ウェブサイトの紹介ページ、展示会の画面で流す。

主役によって組み方が変わる。

- **製品（画面のある主役）:** 画面の操作と結果で見せる。
- **サービス（形の無い主役。支援、運用、相談、受託開発など）:** 提供の流れと、受けた後の状態の変化で見せる。

## 組み合わせた構成の型

- 本体は [課題 → 解決 → 証拠](../structures.md)。
- サービスでは、解決の見せ場を [図で組み上げる解説](../structures.md) の組み上げ（提供の流れを1段階ずつ）にする。

## 尺と fps の目安

- 尺: 60〜120 秒。90 秒くらいが多い。
- fps: 30。

## 場面の並びの例

90 秒の場合:

| 秒 | 段 | 中身 |
|---|---|---|
| 0〜5 | つかみ | 一番覚えてほしい一文と、いちばん分かりやすい一画面（サービスなら、受けた後の状態を一言で） |
| 5〜18 | 困りごと | 対象の人と、その困りごと。2〜3カット。具体の場面（誰が、いつ、何に時間を取られているか） |
| 18〜65 | 解決の見せ場 | 下の「見せ場の作り方」 |
| 65〜80 | 証拠 | 渡された事例、数値、声、対応環境、資格、体制。無ければ「使い始めるまでの流れ」か「提供範囲（できること・できないこと）」に置き換える |
| 80〜90 | 締め | 一文の再掲、ロゴ、問い合わせ先や URL。最後の 1.5〜2.0 秒は止める |

- 60 秒版: 見せ場を 18〜45 秒（機能2〜3つ、または段階3つ）、証拠 45〜52 秒、締め 52〜60 秒。
- 120 秒版（製品）: 機能を5つまで。5つ目以降は1画面に並べた一覧で見せる。

## 見せ場の作り方

**製品が主役のとき**

- 機能を3〜4つ、1機能 10〜15 秒。各機能を「操作 → 結果」の順に見せる。
- 機能の間に、製品の全体像に戻るカット（3〜4 秒）を挟むと、今どこを見ているかが分かる。
- 操作する場所を示す。寄りは `ms.ease.inOutCubic` で 500〜800ms。
- 画面のスクロールは `ms.ease.outQuint` で、1 秒あたり画面の高さの 50% 以下の速さにする（速いと文字がにじむ）。
- 画面の扱いは [content-rules.md](../content-rules.md) の「製品画面」に従う。

**サービスが主役のとき**

- 提供の流れを3〜5段階の図で見せる（例: 相談 → 設計 → 導入 → 運用）。1段階 8〜10 秒。
- 図は1段階ずつ組み上げ、今の段階をアクセント色で示す。段階ごとに「誰が何をするか」「受け取る物」を1行で。
- 図の要素は前の段階から次の段階へ受け渡す（矢印が伸びて次の箱になる）。毎回一から描き直さない。
- 提供の流れ、期間、価格、体制は渡されたものだけ（[content-rules.md](../content-rules.md) の「価格、期間、約束」）。

**どちらでも**

- ナレーションがあるなら、先に合成して秒数を確定させ、画面の動きをナレーションの区切りに合わせる。テロップは要点の短い言葉にする。

## よくある失敗

- 機能を全部入れようとして、どれも説明不足になる。
- 画面録画をそのまま早送りで流し、何が起きたか分からない。
- 「伴走」「ワンストップ」のような抽象語だけで、何をしてくれるのかが分からない。
- 流れの図を一度に全部出し、どこを見ればよいか分からない。
- 締めに問い合わせ先が無い、または読む時間が無い。
