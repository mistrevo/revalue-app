# 01 foundation（基盤）

## 目的

利用者が安心して始められ、いつでもやめられる土台を作る。あわせて、main ブランチに入った変更が公開 URL に自動で出る仕組みを最初に通す。こうすると、あとのまとまりを公開 URL で確かめられる。

達成するユースケースは「始める」と「やめる」（[2-usecases.md](../prd/2-usecases.md)）。まとまりをまたぐ決まりは [00-common.md](00-common.md)、技術の決まりは [00-tech-stack.md](00-tech-stack.md) にある。

## 振る舞い

### 画面

| 画面 | パス | ログイン | 中身 |
|---|---|---|---|
| 案内 | `/` | 要らない | RE:VALUE が何をするか。先に「本人の言葉を根拠にする」「本人が選び、直せる」を伝える。約束 3 つを題と 1 行で。進め方を 1 行で。「Google でログインして始める」ボタンは下。ログインして了解した人はトーク（`/talk`）へ、了解していない人は「はじめに」へ送る（開いたらトークが出るように。Claude の判断） |
| はじめに | `/start` | 要る | 4 行の要約（残すもの、残さないもの、AI に送るとき、保存期間と全部消せること）と、「くわしく読む」の中の 5 項目の全文（保存するもの、保存しないもの、使い道、保存期間、いつでも全部消せること）。要約は短いので全部は挙げないが、「〜だけ」と言い切って全文より狭く読ませない（Claude の判断）。「くわしく読む」には開く印（下向きの矢印）を付ける。「了解して始める」ボタンと、了解しない人の出口「了解せずにやめる（ログアウト）」（ログアウトへページごと移動し、その端末のブラウザに残した書きかけも消す。Claude の判断）。了解したら、トーク（`/talk`）へ進み、新しい場面の最初の問いが出る。了解済みなら、トークへ進める |
| 話す（入口） | `/talk` | 要る（了解も） | 開いたときの行き先を決めて、その場面を出す（[02-discover.md](02-discover.md) の「開いたときの行き先」）。古いリンクの `/home` も、ここへ送る |
| 設定 | `/settings` | 要る | 「色」（6 色から選ぶ。この端末にだけ残す）、「全部消す」、ログアウト。全部消したときと、ログアウトするときは、その端末のブラウザに残した書きかけも消す |

- ログインは `/.auth/login/google?post_login_redirect_uri=/start` へ、ページごと移動して行う。ログアウトは `/.auth/logout?post_logout_redirect_uri=/`
- ログインしていない人がログインの要る画面を開いたら、案内の画面へ戻す。画面にないパスも、案内の画面へ戻す（Claude の判断）
- 了解していない人が了解の要る画面を開いたら、「はじめに」の画面へ進める
- 「はじめに」に書くこと
  - 保存するもの: 話した内容、AI の見立て、5 つの記録（できること、好み、やりたいこと、条件、動き出すときに大事にしたいこと）、選んだ案と最初の一歩、可能性レポート（確かめた力や選んだ案を一つにまとめたもの）。あわせて、ログインした人を見分ける ID（元に戻せない形に変えたもの）、了解した日時、その日の送信回数と最後に使った日
  - 保存しないもの: 名前、メールアドレス、Google のプロフィール。あわせて、書きかけの答えは送るまでその端末のブラウザにだけ残り、サーバーには送らないことと、消えるとき（送る、区切る、飛ばす、全部消す、ログアウト、書いてから 30 日）。家族と共用する端末では次に開いた人の目に入りうるので、そのことも添えて、了解する前に知らせる（[02-discover.md](02-discover.md) の「書きかけを残す」。Claude の判断）
  - 使い道: 返事、見立て、仕事の選択肢を作るためと、選んだ案を深めるために、話した内容、5 つの記録、選んだ案を AI（Anthropic の Claude）に送る。それ以外は、本人が見返し、続きから話すためだけに使う。開発者も話した内容を読まない。人数として数えるのは、可能性レポートまで進んだ人の数と、案を選んだ人の数だけで、誰のことかは分からない形にする
  - 保存期間: 最後に使った日から 30 日たつと、自動で消える
  - いつでも、設定の画面から全部消せる
- 「全部消す」は、画面の中でもう一度確かめてから消す。消したあとは、「はじめに」の画面へ進め、全部消したことと、また始められることを一度だけ伝える
- 送信回数の上限を超えたときは、「今日はここまでにしましょう」のように穏やかに伝える。日本時間の翌日 0 時からまた話せることも添える。この表示の部品はこのまとまりで作り、02 discover（話す）の画面で使う。画面ごとの言い方は [00-common.md](00-common.md) の「言葉」に書く

### API

| メソッドとパス | ログイン | 了解 | 返すもの |
|---|---|---|---|
| `GET /api/health` | 要らない | 要らない | 200。動いていることと、イメージを作ったコミット（デプロイのあとに、新しいイメージが動いているかを確かめるのに使う） |
| `GET /api/me` | 要る | 要らない | 了解したかどうかと、了解した版（「はじめに」の中身の版） |
| `POST /api/consent` | 要る | 要らない | 204。了解の記録（いつ、どの版に）を残す |
| `DELETE /api/me` | 要る | 要らない | 204。その人のデータをすべて消す |
| `GET /api/stats` | 要る | 要る | 人と結びつかない数（可能性レポートまで進んだ人、案を選んだ人）。了解した人ならだれでも見られる（Claude の判断） |
| `GET /api/next-step` | 要る | 要る | 次にできること一つ（`step` と、話している途中の場面なら `episodeId`）。決め方は [00-common.md](00-common.md) の「次にできること」。AI を呼ばないので、1 日の送信回数は使わない。ログには時間だけを書く |

- ログインしていない人が `/api/health` 以外の `/api` を呼んだら、401 を返す。了解が要る API に、了解していない人が来たら 403 を返す。要求の途中で全部消されて書けなかったときも 403 を返す。どちらも ProblemDetails（エラーを決まった形の JSON で返す標準）で、種類（`type`）で見分けられるようにする
- `/api` 以外の知らないパスには `index.html` を返す
- 了解の版は日付の文字列で持つ（同じ日に上げたときは `-2` のように番号を添える）。いまの版は `2026-11-06`。「はじめに」の中身を変えたら版を上げ、了解し直してもらう（Claude の判断）

### ログインと利用者キー

- 本番のログインは、Container Apps の組み込み認証（アプリの手前でログインを受け持つ機能）で行い、Google を使う。組み込み認証は、ログインしていない人も通す設定にする
- 裏側は、組み込み認証が付けるヘッダー `X-MS-CLIENT-PRINCIPAL-IDP` と `X-MS-CLIENT-PRINCIPAL-ID` だけを読む。このヘッダーは外からは付けられず、組み込み認証が付けたときだけある（[公式ドキュメント](https://learn.microsoft.com/azure/container-apps/authentication)）。名前やメールアドレスの入ったヘッダーは読まない
- 利用者キーは、「プロバイダー名:ID」を HMAC-SHA256（鍵を使って元に戻せない値に変える方法）で変換し、先頭に `u_` を付けた文字列にする。鍵は設定 `Auth__UserKeySecret` から読み、なければ起動を止める。開発環境（Development）だけは、鍵がなければ起動ごとの乱数を鍵にする。手元はインメモリの保存先で、止めればデータも消えるので困らない（Claude の判断）
- 開発環境（Development）だけ、偽のログインを使う。`/.auth/login/google` と `/.auth/logout` を裏側が受け、開発用の利用者でログインした状態にする。開発用の利用者はクッキーで覚え、`dev_user` を付けると別の利用者に切り替えられる。本番では、この偽のログインは動かない
- テストでは、組み込み認証と同じヘッダーを付けて、利用者を切り替える

### データの保存

- Cosmos DB（Azure のデータベース）のコンテナ（データの入れ物）1 つに、利用者キーをパーティションキー（データを分けて置く基準）にして保存する
- アイテム（保存する 1 件ずつのデータ）の種類は `type` で分ける
- 人と結びつかない数と、アプリ全体の送信回数は、利用者キーと重ならない `global` というパーティションに置く（Claude の判断）
- 手元とテストでは、同じ形で動くインメモリの保存先（メモリの中だけに置き、止めると消える）を使う。設定 `Cosmos__Endpoint`（Cosmos DB の URL）がなければ、インメモリで動く。ただし本番（Production）では、`Cosmos__Endpoint` がなければ起動を止める。データが残らないまま動き続けないため（Claude の判断）
- このまとまりで持つアイテムは、了解の記録、使った記録（その日の送信回数と、最後に使った日）、数えたしるし（その人を一度数えたか）
- その人のパーティションに書けるのは、了解の記録があるときだけ。了解の記録がないときは何も書かず、その要求は 403 になる。保存先がこれを守り、Cosmos DB では了解の記録を読む操作と書く操作を一つのトランザクション（まとめて成功するか、まとめて失敗する処理）にする（Claude の判断）
- 全部消すときは、了解の記録を最初に消す。全部消すのと同じ人のほかの要求が重なっても、消したあとに届いた書き込みは断られ、データが作り直されない（Claude の判断）

### 自動で消す

- その人のアイテムには、すべて 30 日の TTL（決まった時間がたつと自動で消す設定）を付ける
- いまの版で了解した人が、日本時間でその日に初めて API を使ったとき、その人のアイテムをすべて書き直して、30 日を数え直す
- 了解していない人には、使った記録を作らず、ほかのアイテムも書き直さない。全部消したあとに画面が了解の状態を読み直しても、何も残らないようにするため（Claude の判断）
- TTL はアイテムごとに書いた時刻から数えるので、了解の記録が先に消え、同じ日のあとで書いたアイテムだけが少しのあいだ残ることがある。了解の記録がない人のアイテムが残っていたら、その人の次の要求で消す。了解し直したときに、前の残りが戻らないようにするため（Claude の判断）
- インメモリの保存先も、時計を差し替えて TTL を再現する。テストでは時計を進めて確かめる

### 送信回数の上限

- 1 人 1 日 100 回、アプリ全体で 1 日 1,000 回まで。数は設定 `Limits__MessagesPerDay` と `Limits__MessagesPerDayTotal` で変えられる
- 上限は、AI に送る API にだけ付ける。API ごとにフィルター（要求の前に処理を挟む仕組み）を 1 行で付けられるようにし、02 discover（話す）から使う
- 上限を超えたら、429（送りすぎを知らせる応答）を ProblemDetails で返し、次に送れる時刻（日本時間の翌日 0 時）を添える
- 回数は先に 1 増やし、増やしたあとの値で上限と比べる。同時に送られても、上限を超えて通さないため。断った分も、その日の回数に残る（Claude の判断）
- 1 人の上限で断った要求は、アプリ全体の回数を増やさない。1 人が送り続けても、ほかの人の分を使わないため（Claude の判断）
- 1 人分の回数は、その人のパーティションに 1 件だけ置き、日付と回数を持つ。日付が変わったら 1 から数え直し、前の日の回数は残さない（Claude の判断）
- 全部消すと、その人のその日の回数も消える。それでも、アプリ全体の上限でクレジット（配布された Claude API の利用枠）の使いすぎは防げる（Claude の判断）

### 人と結びつかない数

- 「可能性レポートまで進んだ」「案を選んだ」を、1 人 1 回だけ数える仕組みを作る。数えたかどうかのしるしは、その人のパーティションに置く。数そのものは `global` に置き、利用者キーを持たない
- しるしは「なければ作る」で置き、作れたときだけ数を増やす。同じ人を同時に数えても、1 回だけ増えるようにするため（Claude の判断）
- 数える呼び出しは、05 options（仕事の選択肢）と 07 report（可能性レポート）から使う。このまとまりでは仕組みとテストだけを作る
- 全部消すとしるしも消えるので、同じ人がもう一度数えられることがある（Claude の判断）

### ログ

- 何をログに書いてよいかは、[00-common.md](00-common.md) の「データ」に従う
- アクセスログは 1 リクエストに 1 行で、メソッド、経路の型（`/api/me` のようなもの。実際のパスやクエリは書かない）、状態コード、かかった時間、利用者キーだけを書く

### 公開 URL に出す仕組み

- `infra/main.bicep` に、[00-tech-stack.md](00-tech-stack.md) の「Azure の構成」のリソースを定義する。組み込み認証（Google）の設定も含める
- Google 側に登録したアプリのクライアント ID は、Bicep のパラメーター（作るときに外から渡す値）で渡す。対になるクライアントシークレット（鍵）は、Key Vault の `google-client-secret` から読む
- `Dockerfile` は、画面を作る → 裏側を publish → 実行用の小さいイメージ、の 3 段にする
- `.github/workflows/ci.yml` は、PR と push のたびに、裏側のビルドとテスト、画面のビルドとテスト、フックのテスト、`infra/main.bicep` のビルド（`az bicep build`）を回す。あわせてコンテナのイメージを作って起動し、`/api/health` が 200 と、作ったコミットを返すことを確かめる
- `.github/workflows/deploy.yml` は、main に push されたときに動く。文書（`docs/` と `*.md`）だけの変更では動かない（Claude の判断）。コンテナのイメージを `ghcr.io` に push し、Container App を新しいイメージに更新する。最後に、公開 URL の `/api/health` が今回のコミットを返し、`/` が 200 を返すことを確かめる。新しいリビジョン（Container App の版）が起動に失敗すると古いリビジョンがそのまま応答するので、200 だけでは確かめたことにならないため
- Azure の準備がまだ（リポジトリ変数 `AZURE_CLIENT_ID` がない）ときは、`deploy.yml` はデプロイを飛ばしてそう知らせ、失敗にはしない（Claude の判断）
- Azure へは OIDC（鍵を保存せずに、その場かぎりの証明でログインする仕組み）でログインし、鍵を GitHub に置かない
- Azure の場所やリソースの名前は、GitHub のリポジトリ変数（鍵ではない設定）で渡す
- 次の作業だけは手で行う。[00-tech-stack.md](00-tech-stack.md) の tech-3（作り直せる）にあたる。手順は `infra/README.md` に書く
  - 開発者: Google 側でログイン用のアプリ（OAuth クライアント）を作り、同意画面を「本番」として公開する。Key Vault に `anthropic-api-key` と `google-client-secret` の値を入れる
  - 開発者かエージェント: 最初の 1 回の `az deployment group create`。Key Vault の `user-key-secret` は乱数から作って入れる。`ghcr.io` のイメージが非公開で作られたら、公開にする

## 受け入れ基準

1. foundation-1（案内はログインなしで見られる）: ログインしていない人が `/` を開くと案内が出る。`/api/health` 以外の `/api` は 401 を返す。ログインの要る画面は案内へ戻す。確かめ方: 裏側の結合テスト（裏側を丸ごと立ち上げて API を呼ぶテスト。各 API に未ログインで要求する）と、画面のテスト
2. foundation-2（始める前に保存するものを示す）: 初めてログインした人は、了解するまで、了解の要る API を使えない（403）。了解するまで、その人のアイテムを作らない。「はじめに」の画面に、4 行の要約が先に出て、上の 5 つの項目の全文が「くわしく読む」の中（閉じていてもページの中）にあり、了解しない人の出口（ログアウト）がある。要約は「〜だけ」と言い切らない。前の版で了解した人は、了解し直すまで了解の要る API を使えない。了解すると記録が残り、`GET /api/me` が了解済みを返す。確かめ方: 結合テストと、画面のテスト（要約と、項目の文言がページにあるか）
3. foundation-3（いつでも全部消せる）: `DELETE /api/me` のあと、その人のアイテムが 1 件も残らず、`GET /api/me` が了解していないことを返す。そのあと `GET /api/me` を呼んでも、アイテムは 0 件のまま。同じ人のほかの要求と重なっても、消したあとに 1 件も残らない。ほかの人のデータと、人と結びつかない数は残る。画面では、もう一度確かめてから消し、「はじめに」の画面へ進んで、消し終えたことを伝える。確かめ方: 結合テスト（2 人分のデータを作って 1 人だけ消す。ほかの要求と同時に消す。書き込みの直前に、消す処理を割り込ませる）と、画面のテスト
4. foundation-4（使わなければ自動で消える）: 最後に使ってから 30 日たつと、その人のアイテムが消える。29 日目に使うと、そこから 30 日残る。同じ日のあとで書いたアイテムも、了解の記録が消えたあとに残さず、了解し直しても戻らない。確かめ方: インメモリの保存先で時計を進める結合テスト。Cosmos DB では、アイテムに `ttl` が付くことを確かめる単体テスト
5. foundation-5（名前とメールアドレスを残さない）: 利用者キーは、同じ人なら同じ値、違う人なら違う値になり、元の ID を含まない。名前やメールアドレスの入ったヘッダーを付けて要求しても、保存したアイテムとログに、その文字列が出ない。本番の設定では、偽のログインのヘッダーや経路が効かない。確かめ方: 単体テストと結合テスト（保存したアイテムとログを集めて文字列を探す）
6. foundation-6（使いすぎを穏やかに止める）: 上限のフィルターを付けた API に、1 人の上限を超えて送ると 429 が返り、次に送れる時刻（日本時間の翌日 0 時）が付く。アプリ全体の上限でも同じ。同時に送られても、上限を超えて通さない。日本時間の 0 時を過ぎると、また送れる。日付が変わったあと、その人のパーティションに前の日の回数は残らない。画面の部品は、穏やかな言葉と次に送れる時刻を出す。確かめ方: テスト用の API にフィルターを付け、時計を差し替えて回す結合テスト（同時に送るものを含む）。画面の部品のテスト
7. foundation-7（公開 URL で動く）: PR で `ci.yml` が通る。main に入ると `deploy.yml` が動き、公開 URL の `/api/health` が今回のコミットを返し、`/` が 200 を返す。幅 375px の画面と PC の画面で、案内が崩れずに出る。確かめ方: このまとまりの PR では `ci.yml`（`infra/main.bicep` のビルドと、コンテナが作ったコミットを返すことを含む）が通ることを確かめる。公開 URL の確認は、main に入れたあとに `deploy.yml` の結果と Playwright（実際のブラウザで動かす道具）で行う
8. foundation-8（数だけを数える）: 同じ人を何度数えても、同時に数えても、1 回だけ増える。数のアイテムは利用者キーを持たない。全部消しても数は減らない。確かめ方: 結合テスト（同時に数えるものを含む）

## やらないこと

- 話す画面と、AI の呼び出し。02 discover（話す）で作る。このまとまりでは Claude を呼ばない
- 数える呼び出しを、実際の画面の動きにつなぐこと。05 options（仕事の選択肢）と 07 report（可能性レポート）でつなぐ
- Google 以外のログイン、合言葉、許可リスト
- 開発者が数や中身を見るための管理画面。数は `GET /api/stats` で見る
- 独自ドメイン

## 評価との対応

- このまとまりは AI を使わないので、架空エピソード集での評価はない
- 画面の文言は、[00-common.md](00-common.md) の common-1（使わない言葉を出さない）のテストで確かめ、言い方は voice-reviewer で点検する
