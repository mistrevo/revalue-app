# ペルソナ評価の取り込みと、聞き方を育てる仕組み（設計）

2026-11-05。開発者との相談で決めたことを、変更の経緯として残す。正しい姿は PRD と Spec に書く。

## なぜ

- 11/4 に、架空の 6 人（ペルソナ）を AI が演じて、手元の RE:VALUE を最初の画面から可能性レポートまで通した。6 人とも最後まで着いたが、問いが本題から外れて「試された」と感じた人が多く、根拠の薄い力が出る場面もあった
- その評価は、構想用の別のリポジトリから回した。人物と結果がこのリポジトリの外にあり、回す道具も一時フォルダの使い捨てだった。このままでは、直したあとに同じ条件で回して比べられない
- 当事者の協力者から、最初の問いについて一言もらった。「最近の一日」ではなく「〜と感じた日」を聞く。成功体験や達成感、失敗、立ち直りを引き出す方向にする
- 当事者の協力者が、ゴールのレポートと、そこへたどり着く聞き出し方のイメージを書いてくれる（まだ届いていない）。届いたら、それをもとに聞き方と、力を確かめる物差しの精度を上げていく。直すたびにペルソナで比べたい

## ゴール

1. PRD に足した 08 revisit（別の日に話す）と新しい最初の問いを、Spec とコードまで作り、公開 URL で試せるようにする
2. このリポジトリで開いたセッションに「ペルソナ評価を回して」と言うだけで、サーバーの起動から結果のまとめまで回り、前の回と比べられる
3. 当事者の協力者のレポートが届いたら、その日のうちに聞き方を直し、ペルソナで直す前と後を比べられる

## やらないこと

- 製品の裏側で、API の Agent Skills やエージェントの仕組みを使う（理由は「3. 聞き方の型」）
- ペルソナ評価の結果から、AI 同士の判定だけで言い方を確定する。直すかどうかは開発者が結果を読んで決める
- 公開版（Google ログイン、Cosmos DB）でペルソナを回す
- 直す候補のうち、当事者の協力者のレポートで変わりうるものを先に直す（下の表の「待つ」）

## 失敗とみなすこと

- 公開リポジトリに、実在の人の名前、開発者の名前、開発者の家族を指す「提案者」「奥さま」、当事者の協力者の体験や家庭の事情が入る。架空の人物の会話に出る「奥さま」（C の架空の妻を AI がそう呼んだもの）は、架空の記録なのでそのまま残す
- 参考図書の文を写す
- 演じる役が評価の物差しを知り、足りない行動を先回りして話す（評価の意味がなくなる）
- 最初の問いを変えたことで、「私には何もない」と思っている人が答えにくくなる

## 1. 修正案を取り込む

### PRD

- メインの作業ツリーにある、コミットしていない変更を、main の最新（PR #16 のあと）に載せてコミットする。PRD の 7 ファイル、`docs/decisions/2026-11-04-revisit.md`、progress.md の 1 行。progress.md は両方で直しているので、中身を合わせる
- 最初の問いの変更を PRD に足す
  - discover-1（具体的な一日を一つ聞く）: 「最近の具体的な一日」を「最近の、気持ちが動いた具体的な一日」にする。うまくいったと感じた日、大変だったけど乗り切った日、思うようにいかなかった日から選べるようにする
  - 4-rules.md の「別の日の入口」で、「それ以外」の人に示すきっかけ（いまは「予定がずれた日」「用事が重なった日」「いつもと違うことがあった日」）を、最初の問いと同じ 3 つにそろえる（Claude の判断）
  - 言葉は仮で、当事者の協力者のレポートを見て変える
- 理由は `docs/decisions/2026-11-05-opening-question.md` に残す

最初の問いの仮の形（Claude の判断。voice-reviewer で点検し、開発者に確かめてもらう）:

> 最近、気持ちが動いた日のことを、一つ聞かせてください。どんな日でしたか？
>
> 選択肢: うまくいったと感じた日 / 大変だったけど、乗り切った日 / 思うようにいかなかった日

- 選択肢は、特定の力の核となる行動に寄らない（いまの決まりのまま）。気持ちの向きで分け、うまくいかなかった日も同じ重さで並べる。「私には何もない」と思っている人が、成功の話だけを求められていると感じないようにするため
- 選んだだけでは根拠にしない（validate-5（選んだだけでは根拠にしない））。選んだあとは、その日の具体的な出来事を聞く
- 2 つ目からの場面の問いと、「この話は飛ばす」のあとの問いをどうするかは、Spec を書くときに決める。飛ばしたあとは重い日に話を戻さない決まりがあるので、「思うようにいかなかった日」は出さないのがよいと見ている

## 2. ペルソナ評価をこのリポジトリで完結させる

### 回し方（開発者から見て）

1. revalue-app でセッションを開き、「ペルソナ評価を回して」と言う（スキル persona-eval が動く）。人を絞るときは「A と B だけ」のように言う
2. セッションが、鍵の確認、サーバーの起動、6 人の演技、機械での確かめ、評価、まとめまでを回す
3. 終わると、`evals/results/<日付>-persona.md` にまとめが、`evals/results/<日付>-persona/` に人ごとのやりとりの全文ができている。前の回との違いもまとめに入る
4. 開発者がまとめを読み、直すものを決める

- 結果は、まとめも全文も公開する。開発者が「ペルソナは架空なのでよい」とした（11/5）。芯に反する振る舞いが出た記録も、直した経緯として残す

### 役割

| 役 | 読むもの | 読まないもの | モデル |
|---|---|---|---|
| 演じる役（1 人ずつ別に） | 自分の人物ファイル、演じ方 | ソースコード、Spec、PRD、評価の見方、ほかの人物 | Sonnet（11/4 と同じ） |
| 評価する役 | 評価の見方、PRD、やりとりの全文、機械の確かめの結果 | — | Opus |
| まとめる役 | 評価の結果、前の回のまとめ | — | Opus |

- 演じる役と評価する役を分ける。物差しを知っていると、足りない行動を先回りして話してしまうため（11/4 と同じ）
- 演じる役は画面を動かすのにシェルを使うので、「読まない」という指示だけでは防げない。使える道具を画面の操作に限るなど、できる範囲で仕組みで止める（作り方は builder に任せる）。評価する役は、演じる役が人物ファイルにない行動を足していないかも見る
- 機械で確かめられること（引用が一字一句同じ、使わない言葉、状態の呼び名、条件の範囲、登録した職種、横のはみ出し）は、AI ではなくスクリプトで確かめる。11/4 の道具にある
- 聞き方の物差し（当事者の協力者のレポートから書くもの）ができたら、評価する役が読むものに足す
- エージェントは 10 体未満にする（演じる役 6、評価する役とまとめる役で 3 まで）

### サーバー

- スキルが自分でサーバーを起動する。画面をビルドし、裏側を `evals/personas/.run/server` に書き出して、`.env` の鍵で `http://localhost:5080` に起動する。書き出したものから動かすのは、Windows ではビルドの結果がロックされ、ほかのビルドとテストが止まるため
- 鍵は値を表示せずに確かめる。最初の返事が偽の AI の決まった返事なら止める
- 08 revisit の「別の日」を通すには、手元のサーバーの日付を進める手段が要る。製品のコードなので、08 revisit のまとまりで作る。開発モードのときだけ使え、ログインした人ごとに進められる形にする（6 人が同じサーバーを使うため。作り方は builder に任せる）
- 08 revisit を通すために、2〜3 人の人物ファイルに「2 日目」の出来事を足す（誰にするかは builder に任せる。最後に全部消す E は向かない）

### 費用

- 6 人で 1 回 $7 くらい（11/4 の見積もり）。回すたびに progress.md の「使った額」に書く
- 人を絞って回せるようにする

## 3. 聞き方の型

### 考え方

場面によって、引き出し方は違う。「私には何もない」と言われたとき、失敗の話が出たとき、立ち直りの話が出たときでは、聞くことも聞き方も変わる。その知恵を「型」として場面ごとに持ち、要る場面でだけ発動する。考え方は Agent Skills（必要なときだけ専門の知恵を読み込む）に倣う。

### 作り方（開発者が決めた）

- 発動を決めるのはコード。読み取りの AI（reader）が答えの場面を見分け、コードが場面に合う型を選び、聞き手の AI（listener）へのその往復の指示に足す
- 型は `src/Revalue.Server/Ai/Prompts/` の下に、型ごとのファイルで置く。評価からも同じファイルを読む
- API の Agent Skills は使わない。コード実行の環境と組み合わせて動く仕組みで、1 往復ごとに呼ぶ会話では待ち時間が延びる。いまは「コードが次の一手を決め、AI は言葉にする」形で、芯 1（根拠のない力は出さない）と芯 2（突き放さない）をテストで守っている。この形を崩さない
- いまの次の一手ごとの指示（「何もない」への応え、病気の話から本人のしたことに戻す、など）が、型の最初の中身になる
- 毎回同じ指示はキャッシュが効く位置に置き、型はそのあとに置く

### 進め方

1. 器（順番 6）: 08 revisit と直す候補が main に入ってから作る。中身はいまの指示を移すだけで、振る舞いは変えない。評価を回して、変わっていないことを確かめる
2. 中身（順番 7）: 当事者の協力者のレポートが届いたら、
   - ゴールの姿と聞き出し方を「聞き方の物差し」として、PRD の 4-rules.md の対話の決まりに書く
   - 型の中身を書き、型を選ぶための場面の見分け方を読み取りに足す
   - 評価する役が読むものに、聞き方の物差しを足す
   - ペルソナで、直す前と後を比べる
3. 参考図書（開発者が挙げた 3 冊）は、要点を私たちの言葉で書き起こし、型の中身に溶かす。本文は写さない。書名と著者は、文書に書く前に確かめる

### 当事者の協力者のレポートの扱い

- リポジトリに入れるのは、ゴールの形と聞き出し方を、私たちの言葉で書き起こしたものだけ。協力者の体験や家庭の事情は書かない。原本は入れない
- 「妻へのインタビュー」と書くのはよい（開発者、11/5）。協力者の声を引くときは、個人が分かる部分を除く

## 開発者が決めたこと（11/5）

- 修正案は、作業ツリーにある PRD の 08 revisit。Spec とコードまで作る
- 最初の問いを「〜と感じた日」を聞く形に変える（当事者の協力者の一言から）。協力者のレポートを読んで、聞き方はまた変える
- ペルソナ評価を、このリポジトリだけで回せるようにする
- 聞き方の知恵は場面ごとの型にし、コードが選んで渡す。Agent Skills は使わない
- 公開リポジトリに、実在の名前、開発者の名前、「提案者」「奥さま」を書かない。ペルソナは架空なのでよい
- 直す候補は、いまやるべきものを進める。協力者のレポートが届いたら共有してもらう

- 別の日の入口のきっかけを、最初の問いと同じ 3 つにそろえる
- 直す候補の分け方（いま／待つ）。4（「まだ」の言い方）は、PRD の呼び名に関わるので待つ側にした

- 演じる役は Sonnet、評価とまとめは Opus
