# 能力辞書と業務マスター（設計）

2026-11-05。開発者との相談で決めたことを、変更の経緯として残す。正しい姿は PRD と Spec に書く。

## なぜ

- 当事者の協力者から、ゴールの姿と聞き出し方のイメージを受け取った（2026-11-05。テキスト、まとめの文書、能力辞書と業務マスターの表）。中身は次のとおり
  - 話から能力の候補を見つける
  - 能力ごとに「その能力を感じる行動」を根拠に示す
  - 能力に合う業務を、業務マスターから推薦する
  - 本人の希望と条件で絞る
- いまの RE:VALUE は、力が 3 つ（見立てる、調整する、優先順位をつける）だけで、コードに決め打ちしてある。業務は 3 職種 12 業務で、どれも 3 つの力のどれかにしかつながらない。協力者の考える量（能力 126 項目、業務 120 項目）を入れられる作りになっていない
- 11/4 のペルソナ評価でも、力の名前と引用が並ぶだけで「なぜ力なのか」が伝わらなかった（直す候補 3）

## ゴール

1. 力と業務を、コードではなくデータ（JSON）で持つ。協力者の考える量（能力 126、業務 120）が、データを足すだけで入る
2. 判定に使う力を、いまの 3 つから、協力者のインタビューをもとにした 24 の力に置き換える。芯 1（根拠のない力は出さない）の厳しさは保つ
3. 見えた力に、そう判断した行動と本人の言葉を並べ、仕事のどの場面に役立つかまでつなげる
4. 業務マスターから、条件に合う業務を引いてカードを作る

## やらないこと

- MBTI。運営が避けるべき例に挙げた「性格診断」にあたる
- 身体・実務の軸（手先の器用さ、運転技能など）と、好み・条件の 100 項目を、判定に使うこと。業務の側の条件として持つだけにする
- 正確さの力（正確性、照合力、確認力、注意力）を、日々の話から判定すること。業務の側では「本人に聞いて確かめる条件」として扱う
- 08 revisit（別の日に話す）。このあとに回す（開発者、11/5）
- 自己 PR、職務経歴書の生成。ハッカソンのあとの構想として README と動画で示す

## 失敗とみなすこと

- 一つの話から似た名前の力がいくつも並び、褒めすぎに見える
- 話していない行動を、力の根拠にする（芯 1）
- 協力者が書いた表や文を、そのまま写す。協力者がリポジトリにコミットする
- 「まだ聞けていない力」が 20 以上並び、試験の採点表のように見える

## 開発者が決めたこと（11/5）

- 力の名前と「その能力を感じる理由」は、協力者のインタビューで得たものを基準にする。中身は Claude が書き起こす。協力者の資料は git が無視する置き場所（`.tmp/`）に置き、協力者はリポジトリにコミットしない
- いまの 3 つの力は残さず、辞書の名前と理由に置き換える
- 核となる行動は、理由を自然な切れ目で 2〜3 つに分けたもの。芯 1 の文言を「2〜3 つ」に変える。一つの出来事の中ですべてそろったときだけ「根拠あり」にする決まりは変えない
- 辞書は 126 項目をすべてデータに入れる。ハッカソンの間に判定に使うのは 20〜30 項目で、残りは「準備中」にする

## 1. 能力辞書

### データの形

`src/shared/abilities.json`（画面と裏側の両方が読む。使わない言葉の一覧 `forbidden-words.json` と同じ置き場所）。

| 項目 | 中身 |
|---|---|
| 分類 | 12 の分類（id と名前）。協力者の分類の名前を書き起こす |
| 力 | id（英語の小文字とハイフン）、名前、分類、理由（その能力を感じる行動を 1 文で）、核となる行動（2〜3 つ）、状態（`active` 判定に使う / `preparing` 準備中） |
| 核となる行動 | 番号、行動の文、手がかり（足りない行動を聞くときに聞き手へ渡す言葉。いまの `AbilityText` の手がかりと同じ役目） |

- 126 項目すべてを入れる。名前は協力者の名前を使う（一般的な呼び名なので）。理由と核となる行動は Claude が自分の言葉で書く
- 理由が 1 つの行動にしかならない力は、理由の意図を崩さない範囲で 2 つ目の行動を書き足す。書き足した力には印を付け、協力者に確かめてもらう項目として progress.md に残す
- データの読み込みで、核となる行動が 2〜3 つでない力、分類のない力、id の重なりを止める（テスト）

### 判定に使う 24 の力（Claude の判断）

選び方: 業務マスターの業務につながる力（業務マスターが使う能力名のうち辞書にある 15）、辞書にない名前を近い力に読み替えたもの（7）、協力者が特に挙げた「立ち直り」の回復力、いまの優先順位をつける力を引き継ぐ優先順位設定力。

| 分類 | 力 |
|---|---|
| 人を理解する力 | 情報収集力、違和感察知力 |
| 対話・コミュニケーション | 傾聴力、要約力、質問設計力、言語化支援力、論点整理力 |
| 問題発見・分析・判断 | 仮説思考力、原因分析力 |
| 調整・実行・仕組み化 | 利害調整力、段取り力、優先順位設定力、期限管理力、業務改善力 |
| 家庭・子育て・人間関係から見える力 | 変化への気づき、相手に応じた説明力、予定変更への対応力 |
| 共感・安心・対人支援 | 共感力、不安軽減力 |
| 問い・洞察 | 深掘り力 |
| 実行・挑戦 | 走破力、粘り強さ、回復力 |
| 人事・組織 | 公平性を考える力 |

- 業務マスターの能力名の読み替え: 調整力 → 利害調整力、説明力 → 相手に応じた説明力、改善力 → 業務改善力、構造化力 → 論点整理力、観察力 → 変化への気づき、持続力 → 粘り強さ、対応力 → 予定変更への対応力
- いまの 3 つの置き換え: 見立てる力 → 変化への気づき、調整する力 → 利害調整力、優先順位をつける力 → 優先順位設定力。いまの核となる行動と台本は、置き換え先の行動に書き直して引き継ぐ
- 優先順位設定力の理由は 1 つの行動なので、いまの優先順位をつける力の 3 つ（用事が重なる、先と後を決める、理由や基準がある）を核となる行動にする
- 結果を条件にしない（validate-3（結果で見立てを変えない））。走破力の「最後まで進める」のような結果の言葉は、「続けるために必要な工程を進める」のような行動の言葉に書き換える

### 判定の決まり

- 「根拠あり」: その力の核となる行動が、一つの具体的な出来事の中ですべて確かめられた。本人の言葉を一字一句添える（いまと同じ）
- 「要確認」: 一部だけ確かめられた。または一般論だけ
- 選んだだけの答え、仮の場面の問いの答えだけでは根拠にしない（いまと同じ）
- 一つの句を切り分けて、同じ力のすべての行動の根拠にしない（いまと同じ）

### 見せ方（Claude の判断）

- 一つの出来事から「この話から見えた力」に出すのは、分類ごとに 1 つまで。そろった行動の多い順、同じなら辞書の順。ほかに根拠ありの力があっても、データには残し、画面には出さない。似た力が並んで褒めすぎに見えないため
- 「もう少し聞かせてほしいこと」（要確認）に出すのは、場面ごとに多くて 2 つ。聞き返した力（revisit-4（いまの話を聞き切る）で絞った力）を先にする
- 「まだ聞けていない力」の一覧は出さない。代わりに「ほかの力は、話を重ねると見つかることがあります」のような一文にする（言葉は voice-reviewer で点検し、開発者が確かめる）
- 見えた力には、核となる行動の文と本人の言葉を組にして並べる。印を付けた表（チェック表）にはしない。例:「調子が悪いことに気づいた —『いつもより口数が少なくて』」
- レポートとカードでは、力に「仕事のどの場面に役立つか」（業務マスターの活用場面）を添える

## 2. 聞き方と読み取り

- 読み取りの指示（`reader.md`）の力の表は、判定に使う力からコードが作って差し込む。毎回同じなので、キャッシュが効く位置に置く
- 根拠の `ability` は力の id、`action` はその力の行動の番号。判定に使う力にない id、行動の数を超える番号は、コードが捨てる
- 次の一手（`NextMovePolicy`）、力の状態（`AbilityStates`）、手がかりの言葉（`AbilityText`）は、力の数と行動の数をデータから読む。revisit-4（いまの話を聞き切る）の絞り方はそのまま
- 聞き手の指示（`listener.md`）は、手がかりの言葉を受け取るだけで、力の名前を知らない（いまと同じ。誘導しないため）
- 協力者の深掘りの順（感情 → 出来事 → 気づき → 行動 → 判断の理由 → 結果・変化 → 本人らしい点）は、聞き方の型として次の段で入れる。この段では、最初の問いを協力者の入口の言葉に寄せるだけにする（選択肢「うれしかった日」「困ったことがあった日」「思いどおりにいかなかった日」。Claude の判断）

## 3. 業務マスター

### データの形

`src/Revalue.Server/Features/Options/jobs.json` を、業務マスターの形に置き換える。

| 項目 | 中身 |
|---|---|
| 領域 | 10 の領域（id と名前）。協力者の領域の名前を書き起こす |
| 職種 | 「選ぶ」のカードに出す職種。職業情報提供サイト（job tag）の番号と名前を持つ（いまと同じ）。職種ごとに領域を持つ |
| 業務 | id、領域、職種、名前、何をする仕事か、主な力と補助の力（力の id）、力が業務のどこで生きるか（活用場面）、週の時間、時間帯、場所、時給の目安、要る知識、小さな試し方、状態（`active` / `preparing`） |

- 120 業務をすべて入れる。名前と活用場面は Claude が書き起こす
- カードに使うのは `active` の業務だけ。`active` にするには、週の時間、時間帯、場所、時給の目安、job tag の職種と業務の番号がそろっていること（いまのカードの決まりと同じ。データの読み込みで止める）
- 判定に使う 24 の力それぞれに、`active` の業務が 2 つ以上つながるようにする。家でできる短い時間の業務が多い領域（経理・財務、人事・採用・労務、総務・法務・事務、営業・顧客対応、教育・研修・対人支援）から `active` にする
- 「小さな試し方」は、深めるの最初の一歩の候補の手がかりにする
- 身体・移動の条件（立ち仕事、運転）は、業務の場所と、本人に確かめる条件として持つ。判定には使わない

### カード、深める、レポート

- 「選ぶ」: 見えた力（と確かめ中の力）を主な力に持つ `active` の業務がある職種から、条件に合うものを選ぶ（いまの決まりのまま、力の id で引く）
- 「組み合わせる」: 条件に合う `active` の業務を、力の id で組み合わせる
- 「創る」: いまのまま（需要はまだ確かめていないと示す）
- 深めるの業務の見立て（`PUT /api/deepen/tasks` の `ability`）は、力の id にする
- 画面は力の名前をデータから出す。画面のコードの中の `noticing` などの決め打ちをなくす

## 4. 評価

- 台本（`evals/episodes/`）を、力の id で書き直す。いまの e08〜e19 は置き換え先の力（変化への気づき、利害調整力、優先順位設定力）で書き直す
- 判定に使う 24 の力それぞれに、根拠ありになる台本を 1 本ずつ持つ。分類ごとに 1 本以上、一部だけそろう台本を持つ
- 一つの出来事から似た力がそろいやすい台本（対話・コミュニケーションの力が並ぶ話）を 1 本足し、画面に出す力が分類ごとに 1 つまでかを確かめる
- 合格の線は 6-quality.md のまま（褒めすぎ 0 件、引用の一致すべて、そろった例 9 割以上、足りない行動だけ聞き返す 9 割以上）
- ペルソナ評価の評価の見方（`evals/personas/how-to-judge.md`）の「力の見込み」「カードの見込み」は、作り終えてから書き直す

## 点検で決めたこと（Claude の判断）

設計を読んだ別のエージェントの問いに、次のように答えた。

| 問い | 決めたこと |
|---|---|
| 画面に出さない力を、ほかで使うか | 絞り込みは、本人が力を見るすべての所にかける（話す画面の見えた力、見えた力の画面と履歴、5 つの記録の「できること」、カード、深める、レポート）。画面に出さない力は、カードとレポートの理由にも使わない。本人が見ていない力は外せないため（validate-12（本人が見立てを外せる）、芯 5（本人が選ぶ））。データには残す |
| 台本で、狙っていない力をどう数えるか | 台本には、狙った力の期待する状態と、その話で根拠ありにしてはいけない力だけを書く。それ以外の力は問わない。褒めすぎは、根拠ありにしたすべての力について、引用が核となる行動を本当に示しているか（推し量っていないか）を判定役が見て数える。合格の線は 0 件のまま |
| 業務の値と出典 | いまの jobs.json と同じ前例に従う。職種と業務の言葉は job tag を出典にし、時間、時間帯、場所、時給の目安、使う力は Claude が下書きして、そう明記する。開発者があとで確かめる。job tag のデータ（数値系 ver.7.00、2026-11-03 にダウンロード）は、git が無視する `.tmp/jobtag/` に置き、Workflow から読む |
| 返事が遅くなるか | 読み取りが返すのは見つかった根拠だけなので、出力は力の数に比例しない。力の表は毎回同じで、キャッシュが効く。評価で返事が出始めるまでの時間を測り、11/5 の評価（6〜9 秒）より目に見えて遅くなったら手を入れる |
| 主な力と補助の力 | どちらも「つながる」に数え、カードでも使える力として扱う。Claude が業務の力を付け替えたり足したりしてよい。付け替えた業務には印を付け、協力者に確かめる |
| 公開中のデータ | 古い id（noticing、coordinating、prioritizing）の根拠は、読めない力として無視する。消さず、移さない。話した中身は残る。手順 3 では、いまの 12 業務を新しい力の id に付け替え、手順ごとに公開できる形にする |
| 見えた力に並べる行動の文 | 辞書の共通の文を使い、場面ごとに作らない。読み取りの出力は増えない |

## まだ分かっていないこと

- 24 の力の中に、日々の話から確かめにくい力がないか（公平性を考える力、業務改善力など）。台本とペルソナで見て、確かめにくければ「準備中」に戻す
- 分類ごとに 1 つまで出す決まりで、本人にとって大事な力が隠れないか
- 協力者の考える「能力候補をたくさん見つける」と、似た力を絞って見せることのつり合い。協力者に確かめる
- 業務の時給の目安を、120 業務ぶん出典つきで書けるか。書けない業務は `preparing` のまま
