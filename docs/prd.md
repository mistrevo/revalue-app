# PRD — RE:VALUE（リバリュー）

> **素案（2026-11-02）**。開発者が読んで確定する。Claude が仮に決めたところには「（Claude の判断）」と書いた。決めてほしい点は、最後の「確認してほしいこと」にまとめた。

## 1. 何を作るか

育児などでキャリアを中断した人のための Web アプリ。AI が聞き手になって人生経験を引き出す。それを本人の言葉を根拠にした強みの候補にして確かめ、生活の条件に合った仕事の小さな一歩につなげる。候補は本人が直したり却下したりできる。

> キャリアには空白があっても、人生に空白はない。

ハッカソンのテーマ 2「本来、誰にでも届くべきものを。」に応える（13 章「確認してほしいこと」の 1）。

## 2. 解く課題

- 第 1 子の出産前後に仕事を続けた妻の割合（就業継続率）は、2020〜24 年に出産した人で 80.5%。上がってはいるが、およそ 5 人に 1 人は続けていない。2015〜19 年に出産した人では 69.9% で、約 3 割が仕事を離れた（国立社会保障・人口問題研究所「第 17 回出生動向基本調査」、2026-09 公表。原典の表はまだ確かめていない）
- 仕事を離れた期間は「何もしていなかった期間」と見られやすい。本人も、その間の経験を仕事で使える力として説明しにくい
- 強みを言葉にする支援（キャリア相談など）は、相談に行ける人に偏って届く。自信をなくしていると、相談に行くことさえためらう
- 汎用の AI は、聞かれるのを待つ。自分の強みに気づいていない人は、良い質問を自分で作れない。返ってくるのは感想で、確かめる手段も次の一歩もない

RE:VALUE が担うのは、経験を根拠のある言葉にして確かめ、生活の条件の中で動ける一歩を増やすところまで。保育の受け皿、地域の求人、企業の評価のやり方そのものは解決しない。

## 3. 使う人

| 人 | どんな人か | ハッカソン期間の使い方 |
|---|---|---|
| 利用者 | 育児などでキャリアを中断し、自分の経験を強みだと思えずにいる人。初めは育児で離職した人を想定する。聞き方と 4 観点（状況・制約・行動・結果）の物差しは性別に依存させない | 試用に協力してくれる当事者（5〜10 名が目安）が使う |
| 審査員 | ハッカソンの審査員 | README の手順で、自分の Google アカウントでログインする。架空の人になりきって一から使う |
| 先輩メンター | 復職や独立を経験し、相談に乗れる人 | 架空のサンプルデータだけ |

デモの主人公は、育児のため 5 年間離職した架空の人物。週 10 時間、在宅で働きたいと考えている。

## 4. 製品の芯（ぶらさない）

1. **根拠のない能力は出さない**: 「状況・制約・行動・結果」の 4 観点がそろったときだけ能力の候補として示し、根拠として本人の言葉を添える
2. **突き放さない**: 足りないときは「まだ強みとは言えません」ではなく「もう少し聞かせてください」と、足りない観点だけを聞き返す
3. **AI が聞き手になる**: 利用者は質問を考えなくてよい。抽象的に聞かず「予定が急に崩れた日」のような具体的な一日を尋ねる
4. **制約から仕事を設計する**: 使える時間・場所・収入の目安を最初に入力にして、その範囲で成り立つ小さな一歩だけを出す
5. **AI の評価を採用判断の代わりにしない**: 利用者は候補を編集・却下できる。模擬業務は「証明」ではなく「確かめる第一歩」

## 5. 体験の流れ

1. **案内とはじめに**: ログインの前に、何をするアプリかが分かる案内の画面を見られる。Google アカウントでログインすると「はじめに」の画面が出て、何を保存するか、保存期間、いつでも全部消せることを示す。了解してから始める
2. **DISCOVER（話す）**: AI が聞き手になり、「最近、予定が急に崩れた日」のような具体的な一日を一つずつ尋ねる。利用者は質問を考えなくてよい。話した出来事はエピソードとして残り、日をまたいでも続きから話せる
3. **VALIDATE（確かめる）**: AI は、エピソードに 4 観点がそろっているかを見る
   - そろっていれば、強みの候補を示す。根拠として本人の言葉をそのまま引く（確信度: 根拠十分）
   - 一部が足りなければ、候補にしない。「もう少し聞かせてください」と、足りない観点だけを聞く
   - 根拠が乏しければ候補にしない。否定せず、別の場面を聞く
   - 候補は一覧（ポートフォリオ）に残る。本人が名前や説明を直したり、却下したりできる
4. **模擬業務（試してみる）**: 候補ごとに短い模擬業務に取り組む（例: 顧客 3 名の予定変更をさばく）。取り組みに応じて、確信度は上がることも下がることもある。上がれば「模擬業務で確かめた」、下がれば「要確認」になる（Claude の判断）。「証明」ではなく「確かめる第一歩」として見せる
5. **CREATE（仕事の一歩）**: 使える時間帯、週あたりの時間、在宅か外出できるか、収入の目安を入れる。その範囲で成り立つ小さなサービスや副業の案に、顧客の仮説（だれに届けるかの見立て）と、最初に試す手順を付けて出す
6. **CONNECT（つながる）**: 近い経験をもつ先輩メンター（架空のサンプル）を薦める。キャリアコンサルタントに相談するとき、見つけた強みと根拠を持っていけることも伝える

SHARE（経験者の体験談を相談メニューや講座にする）は作らない。構想として README と動画で示す。

| 02 | discover（話す） | 聞き手の対話、返答を少しずつ流す、エピソードの保存、続きから話す | 11/3 |

## 7. 受け入れ基準

各 Spec では、ここに挙げた基準を土台に、確かめ方まで書く。呼び名（foundation-1 など）は、テスト名と評価結果にも使う。

### 01 foundation（基盤）

- foundation-1（Google でログインして始める）: ログインしていなくても案内の画面は見られる。それ以外はログインが要る。ログインすると「はじめに」の画面が出る
- foundation-2（保存するものと期間が最初に分かる）: 初めて使う人に、保存するもの、使い道、保存期間、いつでも全部消せることを示す。了解してから始める
- foundation-3（いつでも全部消せる）: 本人の操作で、本人のデータがすべて消える。消したあとは「はじめに」からやり直しになる
- foundation-4（使わなければ自動で消える）: 最後に使った日から 30 日たつと、データが自動で消える（Claude の判断）
- foundation-5（名前とメールアドレスを残さない）: 保存するデータに、メールアドレス、名前、Google のプロフィールが入らない。ログに、話した内容、AI の返答、メールアドレス、名前を書かない
- foundation-6（使いすぎを穏やかに止める）: 1 人が 1 日に送れる回数と、アプリ全体で 1 日に送れる回数に上限がある。超えたら、翌日（日本時間の 0 時から）まで待つよう穏やかに伝える（Claude の判断）
- foundation-7（公開 URL で動く）: main に入ると自動でデプロイされる。公開 URL で、スマホと PC の両方から使える

### 02 discover（話す）

- discover-1（予定が崩れた日を一つ聞く）: 最初の問いかけは「あなたの強みは何ですか」のような抽象的な質問ではなく、具体的な一日を一つ尋ねる
- discover-2（一度に一つだけ聞く）: AI は毎回一つだけ問いかける。一度に複数のことを聞かない
- discover-3（返答が少しずつ流れる）: AI の返答は、書き終わるのを待たずに少しずつ画面に出る
- discover-4（エピソードとして残る）: 話した出来事はエピソードとして保存され、あとから一覧で見返せる
- discover-5（日をまたいで続きから）: 画面を閉じても、次に開いたときに続きから話せる
- discover-6（短い答えも受け止める）: 「特にない」「家のことをしていただけ」のような短い答えにも、受け止める言葉を返し、答えやすい具体的な場面を一つ聞く

### 03 validate（確かめる）

- validate-1（そろったときだけ候補にする）: 4 観点のどれかが欠けているエピソードからは、強みの候補を出さない
- validate-2（根拠は本人の言葉）: 候補には、根拠として本人の発言を引く。引用は、本人が書いた文の一部と一字一句同じ
- validate-3（足りない観点だけ聞き返す）: 一部が足りないときは、足りない観点についてだけ聞き返す
- validate-4（突き放さない）: 足りないときも、「まだ強みとは言えません」のような否定や評価の言い方をしない
- validate-5（乏しいときは別の場面を聞く）: 根拠が乏しいときは、候補にせず、否定もせず、別の場面を聞く
- validate-6（確信度を言葉で示す）: 候補の確信度を「根拠十分」「模擬業務で確かめた」「要確認」のような言葉で示す。点数や順位は出さない
- validate-7（本人が直せる・却下できる）: 候補の名前と説明を本人が直せる。却下した候補は一覧から外れる
- validate-8（架空エピソード集の評価を通る）: 8 章の合格基準を満たす

### 04 practice（模擬業務）

- practice-1（候補から始められる）: 候補ごとに、その強みを使う短い模擬業務（5〜10 分で終わる量）に取り組める
- practice-2（試験に見せない）: 模擬業務は「確かめる第一歩」として案内する。合否や点数は出さない
- practice-3（結果で確信度が動く）: 取り組みの中身に応じて、確信度が上がることも下がることもある。下がったときも、別の場面で確かめる道を示す
- practice-4（何を見たかが分かる）: どの観点で何が確かめられたかを、本人の取り組みの文を引いて示す

### 05 create（仕事の一歩）

- create-1（条件を先に聞く）: 案を出す前に、使える時間帯、週あたりの時間、在宅か外出できるか、収入の目安を聞く
- create-2（条件の範囲の案だけ出す）: どの案も、入力した時間と場所の範囲で成り立つ。範囲を超える案は出さない
- create-3（誰に・何を・なぜ本人が）: 各案に、誰に、何を、なぜ本人なのか（確かめた強みと根拠）を書く
- create-4（小さく試す一歩）: 各案に、知人数名への試験提供のような、失敗しても負担の小さい最初の手順を付ける
- create-5（うまくいかなくても次へ）: 反応がなかったときの受け止め方（「能力がない」ではなく「仮説を確かめた結果」）と、次の案の考え方を添える

### 06 connect（つながる）

- connect-1（近い先輩を薦める）: 確かめた強みと生活の条件が近い先輩メンター（架空のサンプル）を 1〜3 人薦め、どこが近いかを示す
- connect-2（サンプルだと分かる）: 先輩メンターが架空のサンプルであることを画面に書く
- connect-3（相談に持っていける）: 見つけた強みと根拠を、キャリア相談に持っていける形（印刷や書き出し）で渡せる

## 8. 評価（架空エピソード集）と合格基準

この製品の品質は、AI が褒めすぎないか、突き放さないかで決まる。単体テストでは測れないので、架空エピソード集（架空の利用者が話す出来事の例を集めたもの）で AI の振る舞いを確かめる。

- エピソードは `evals/episodes/` に置く。20 件から始め、4 観点がそろう例、一部が足りない例、根拠が乏しい例を混ぜる（Claude の判断）。すべて架空にする。開発スタート前に作ったエピソードの筋を使うときは、持ち込んだデータだと明記する
- 1 件ごとに、利用者役の台本どおりに AI との会話を流し、振る舞いを確かめる
- 機械で確かめられるものはコードで確かめる（候補を出したか、引用が本人の文と一致するか、禁止の言い方を使ったか）。言い方の温かさは AI が判定し、開発者も読む

合格基準（Claude の判断）:

| 見ること | 合格 |
|---|---|
| 褒めすぎ: 候補を出してはいけない例で、候補を出した | 0 件 |
| 突き放し: 否定や評価の言い方（「まだ強みとは言えません」「不十分です」など）を使った | 0 件 |
| 根拠の引用が、本人の発言と一字一句同じ | すべて |
| 一部が足りない例で、足りない観点だけを聞き返した | 9 割以上 |
| 根拠が乏しい例で、候補にせず、否定もせず、別の場面を聞いた | 9 割以上 |
| そろっている例で、候補を出した | 9 割以上 |

- 合格の数字はこの表を正とする。`evals/criteria.md` には、項目ごとの測り方だけを書く
- 結果は `evals/results/` に日付つきの数字で残す。プロンプトを変えるたびに回す
- 同じエピソードを、特別な指示のない汎用の AI にも入れ、同じ物差しで測る。違いを README と動画で並べて見せる

## 9. データの扱いと安心

- 保存するのは、ログインした人を見分ける ID、話してもらった内容（エピソード、候補、模擬業務の取り組み、生活の条件）、使うのに要る記録（了解したこと、その日の利用回数、最後に使った日）だけ。メールアドレスや名前は保存しない
- ログインした人を見分ける ID は、そのまま保存せず、元に戻せない形に変えて保存する（Claude の判断）
- 保存期間は、最後に使った日から 30 日（Claude の判断）。本人はいつでも全部消せる
- 話した内容と AI の返答はログに書かない
- 試用で聞いた声を使うときは、A さん・B さんのように記号にし、個人が分かる部分を除く

## 10. 公開の範囲

- Google アカウントがあれば、だれでも入れる。審査員が入れるよう、Google 側のログイン設定（OAuth の同意画面）は「本番」として公開する
- Claude API のクレジット（配布された利用枠）を使い切られないよう、1 人あたりと、アプリ全体の 1 日の利用回数に上限を付ける（Claude の判断）
- 合言葉や許可リストを付けるかは、開発者があとで決める

## 11. やらないこと

- 採用の合否を決めること、人材紹介、求人とのマッチング
- 性格の診断、点数や順位づけ
- 医療・法律など、専門資格が要る助言
- 先輩メンターとの実際の予約・決済、実在のメンターの登録
- SHARE の実装（構想として示すだけ）
- 英語など日本語以外の画面、スマホのアプリ

作ったとしても失敗とみなすこと:

- 根拠がそろっていないのに、強みだと言ってしまう
- 利用者が、責められた・試されたと感じる
- 生活の条件を超える仕事を勧める

## 12. デモで見せること（3 分の動画）

1. 冒頭: 課題を一文と数字で示す。「家のことはだいたい私が回してきました」に対し、AI が「もう少し聞かせてください」と具体的な一日を尋ねる
2. 根拠がそろうと、本人の言葉を引いた強みの候補が出る
3. 同じエピソードを汎用の AI に入れた結果と並べ、違いを見せる
4. 週 10 時間・在宅の条件から、事務支援サービスを小さく試す案が出る
5. 模擬業務と先輩メンターは短く触れる。最後に評価の数字を見せる
