# 別の日に話す仕組みを足す

2026-11-04。PRD の [3-features.md](../prd/3-features.md) の 08 revisit（別の日に話す）と、[4-rules.md](../prd/4-rules.md) の「話の数」「別の日の入口」「カレンダーに入れる」の理由を残す。

## なぜ足すか

手元で架空の利用者を通すと、先週の火曜日の話を 1 つしただけで、2 つの力が可能性レポートに載った。物差しは満たしている。ただ、一つの話で言えるのは「その日そう動いた」までで、開発者は 1 つの話で言い切ることに違和感を持った。そこで、別の日に続けて話せる仕組みを足すと開発者が決めた。

いまのアプリでも別の日の話は足せるが、次の 3 つが足りない（コードと Spec を読んだ範囲で、動かしてはいない）。

- 戻る理由がない。次にできることは可能性レポートで止まる
- 話しても積み上がらない。見せる根拠は新しい話のものに置き換わる
- 2 つ目の話の入口も「最近のある一日」で、何から話すか迷いやすい

## 外した案

線引きは Claude の判断。

| 案 | 外した理由 |
|---|---|
| 根拠ありの条件を上げ、話が 2 つそろうまで力を出さない | 「私には何もない」と思っている人に、最初の発見が届かない。1 回でレポートまで着ける流れとも食い違う |
| 別々の話に出た行動を合わせて、3 つそろったことにする | 一つの出来事の中で確かめる芯 1（根拠のない力は出さない）から外れる |
| 1 回の会話を長くして、3 つの力を全部聞く | 10〜15 分に収まらない。架空の利用者の評価でも、話の途中で別の力を確かめる問いが「試された」と感じさせていた |
| 「くり返し確かめた」のような状態を足す | 点数や評価に近づく。状態は 3 つのまま、話の数を言葉で添える |
| 「あと何回」「進み具合」を見せる | 試験に見え、足りないと言っているように読める |
| 一歩をやったかどうかを記録する | 宿題の確認に見える。その後の話は、ふつうの場面として残す |
| メールやプッシュ通知で知らせる | メールアドレスを持たない決まりと、了解の中身を変えることになる。思い出す手段は、本人が選んだときのカレンダーにする |

## カレンダーを P2 から取り込む

2026-11-05。初めは P2 に置いたが、開発者が 08 revisit（別の日に話す）に取り込むと決めた。メールとプッシュ通知を外したので、アプリの外から思い出せる手段はカレンダーだけになる。入れ方と線引きは Claude の判断。

| 案 | 外した理由 |
|---|---|
| Google カレンダーの権限をもらい、アプリが予定を入れる | ログインで求める権限と、了解の中身が変わる。本人が保存するほうが、芯 5（本人が選ぶ）に沿う |
| 予定に一歩の中身を書く | 家族と共有しているカレンダーで見えることがあり、話した内容が外のサービスに渡る |
| 毎週の繰り返しの予定にする | 宿題や義務に見える |
| 入れたか、予定の日に開いたかを記録する | 宿題の確認に見える。話さなかった人を責める形につながる |

## まだ分かっていないこと

- 当事者の感覚で確かめていない。言い方と入口を協力者に聞いている途中で、返事を待たずに仮の形で作る（[README.md](../prd/README.md) の「決めていないこと」）
- 聞き返す力を一つに絞ると、初回に見える力が減るかもしれない。1 回目の手応えが残るかを試用で見る
- また開きたくなるかは、架空の利用者では分からない。試用者の一部に翌日もう一度開いてもらう
- 同じ出来事を別の場面で話し直しても、話の数が増える。別の日の入口では起きにくいと見ているが、確かめていない
- カレンダーの予定で知らせが出るかは、本人の設定しだいで分からない。また開くきっかけになるかは試用で見る
- 家族と共有しているカレンダーに「RE:VALUE」と出ることを、気にする人がいるかもしれない。見出しは本人がカレンダーの画面で変えられる
