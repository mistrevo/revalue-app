# 3. 機能 — どの機能でユースケースを達成するか

## まとまりと順番

まとまりごとに Spec（`docs/specs/<番号>-<名前>.md`）を書き、この順に作る。01〜08 は、当事者の試用の前に公開 URL で試せる状態にする（試用の日はまだ決まっていない）。

| 順 | まとまり | 達成するユースケース | 優先度 | 目安 |
|---|---|---|---|---|
| 01 | foundation（基盤） | 始める、やめる | P0 | 11/3 |
| 02 | discover（話す） | 経験を話す | P0 | 11/3 |
| 03 | validate（確かめる） | 力を確かめる | P0 | 11/4 |
| 04 | profile（5 つの記録） | 自分を整理する | P0 | 11/4 |
| 05 | options（仕事の選択肢） | 仕事の選択肢から選ぶ | P0 | 11/5 |
| 06 | deepen（選んだ案を深める） | 選んだ案を深める | P0 | 11/5 |
| 07 | report（可能性レポート） | 次の一歩を決める | P0 | 11/5 |
| — | 能力辞書と業務マスター（03〜07 の作り直し） | 力を確かめる、仕事の選択肢から選ぶ | P0 | 11/7 |
| 08 | revisit（別の日に話す） | 別の日にまた話す | P0 | 能力辞書と業務マスターのあと |

- 1 回の利用（10〜15 分）で一つの場面を話し終えれば、可能性レポートまで進めるようにする。また話したら、カードとレポートを作り直す
- まとまりの切り方と目安は Claude の判断。基盤を独立させて最初にデプロイの仕組みを通すと、あとのまとまりは main ブランチに入るたびに公開 URL で確かめられる
- 力の確かめのうち下の 5 つは、場面を話している会話の中で 1 往復ごとに働く。02 discover（話す）は、確かめの仕組みをあとからつなげる形で作る。03 validate（確かめる）で確かめの仕組みを作って会話につなぎ、見せ方、訂正、履歴も作る（Claude の判断）
  - validate-1（すべてそろったときだけ根拠あり）
  - validate-2（足りない行動だけ聞き返す）
  - validate-3（結果で見立てを変えない）
  - validate-5（選んだだけでは根拠にしない）
  - validate-10（一般論には具体的な出来事を聞く）
- 評価の仕組み（架空エピソード集で AI の振る舞いを確かめる仕組み。[6-quality.md](6-quality.md)）は、作りながら精度を上げる。02 discover（話す）で最小のものを作り（Claude の判断）、まとまりごとに確かめる場面を足す

優先度:

- **P0**: 試用とデモに要るもの。01〜07 のまとまりと、能力辞書と業務マスター（[決めたこと](../decisions/2026-11-05-ability-dictionary.md)）。08 revisit（別の日に話す）は、能力辞書と業務マスターのあとに作る（開発者、2026-11-05）
- **P1**: 試用のあとに足す
  - 業務マスターの `preparing` の業務を、条件と出典を足して `active` にする
  - 本人がこれまでの職種を入れて、話を聞く手がかりにする（Claude の判断。開発前の構想メモにある「本人の職種入力」をこう読んだ）
  - 好みとやりたいことを、会話から AI が推し量って足す（Claude の判断。話から好みを読み取ると「性格診断」に見えやすいので、P0 では本人が選ぶか書くだけにした）
- **P2**: 時間が残れば足す
  - 模擬業務（限られた課題を実際にやってみる。例: 日程の調整）
  - 可能性レポートの PDF 書き出し
  - 学ぶ手順（選んだ案に要る知識や道具を身につける順番）
  - 先輩メンターのサンプル表示
  - 話すほどではない日に、一言だけ残す（Claude の判断）

## 要求の書き方

要求は EARS（要求を決まった型で書く方法）で書く。主語は「アプリ」にする。

| 型 | 書き方 |
|---|---|
| いつも | アプリは〜する |
| きっかけ | 〜したとき、アプリは〜する |
| 状態 | 〜の間、アプリは〜する |
| 望まない状況 | もし〜なら、アプリは〜する（しない） |

呼び名は `<まとまり>-<番号>（タイトル）` にし、Spec、テスト、評価の結果でも同じ呼び名を使う。Spec では、要求ごとに確かめ方を足す。

## 01 foundation（基盤）

- foundation-1（案内はログインなしで見られる）: アプリは、ログインしていない人にも案内の画面を見せる。それ以外の画面と API では、ログインを求める
- foundation-2（始める前に保存するものを示す）: 利用者が初めてログインしたとき、アプリは保存するもの、使い道、保存期間、いつでも全部消せることを示し、了解を得てから始める。使い道には、開発者も話した内容を読まないこと、人と結びつかない数だけを数えることを書く
- foundation-3（いつでも全部消せる）: 利用者が全部消す操作をしたとき、アプリはその人のデータをすべて消し、「はじめに」の画面からやり直せる状態にする
- foundation-4（使わなければ自動で消える）: 最後に使った日から 30 日たったとき、アプリはその人のデータを自動で消す
- foundation-5（名前とメールアドレスを残さない）: アプリは、メールアドレス、名前、Google のプロフィールを保存しない。ログには、話した内容、AI の返答、メールアドレス、名前を書かない
- foundation-6（使いすぎを穏やかに止める）: もし 1 日の送信回数が、1 人分かアプリ全体の上限を超えたら、アプリは日本時間の翌日 0 時まで待つよう穏やかに伝える
- foundation-7（公開 URL で動く）: main に変更が入ったとき、公開 URL のアプリが自動で更新され、スマホと PC の両方から使える
- foundation-8（数だけを数える）: アプリは、可能性レポートまで進んだ人の数と、案を選んだ人の数を、人と結びつかない形で数える。本人が全部消しても、その数は残る

## 02 discover（話す）

対話の決まりは [4-rules.md](4-rules.md)。

- discover-1（具体的な一日を一つ聞く）: 利用者が話し始めたとき、アプリは「あなたの強みは何ですか」のような抽象的な問いではなく、最近の、気持ちが動いた具体的な一日を一つ尋ねる。うれしかった日も、思いどおりにいかなかった日も、同じ重さで選べるようにする（問いの決まりは [4-rules.md](4-rules.md) の「最初の問い」）。別の日に始めるときの入口は revisit-3（別の日の入口を用意する）
- discover-2（受け止めてから一つだけ聞く）: アプリは毎回、受け止める一文、本人の行動を映し返す言葉、問い一つ、の順に返す。問いだけを返さない。一度に二つ以上聞かない
- discover-3（選んでも書いてもよい）: 問いを出すとき、アプリは答えの選択肢を 3 つと「それ以外」を示す。自由に書く欄はいつも出しておく
- discover-4（「何もない」も受け止める）: 利用者が「私には何もない」「分からない」と答えたとき、アプリはそれを答えとして受け止め、答えやすい具体的な場面を一つ聞く
- discover-5（つらい話は飛ばせる）: 利用者が話題を飛ばしたいとき、アプリは理由を聞かずに飛ばし、別の場面に移る
- discover-6（一場面ずつ区切り、続きから話せる）: 一つの場面は 5〜8 往復を目安にする。利用者が終えたいとき、または 8 往復に達したとき、アプリはその場面を区切る（Claude の判断）。利用者が画面を閉じても、次に開いたときに続きから話せる
- discover-7（返答が少しずつ流れる）: アプリは、返答を書き終えるのを待たずに、少しずつ画面に出す
- discover-8（話した出来事が残る）: 一つの場面を話し終えたとき、アプリはそれをエピソードとして保存し、あとで一覧で見返せるようにする
- discover-9（病気の詳しいことは聞かない）: もし家族の病気や症状の話が出たら、アプリはその詳しいことを聞かず、本人がしたことに話を戻す（Claude の判断）
- discover-10（つらい状態のサインに応える）: もし本人の心身の不調、家庭内の暴力、死にたいという言葉が出たら、アプリは受け止め、公的な相談窓口を一つ示す。その話は力の確かめに使わない（Claude の判断）

## 03 validate（確かめる）

力を確かめる物差しは [4-rules.md](4-rules.md)。

- validate-1（すべてそろったときだけ根拠あり）: アプリは、力ごとの核となる行動（2〜3 つ）が、一つの具体的な出来事の中ですべて確かめられたときだけ「根拠あり」とする
- validate-2（足りない行動だけ聞き返す）: 場面を話している間に、核となる行動が一部だけ確かめられたとき、アプリは「要確認」とし、足りない行動についてだけ、会話の中で聞き返す。聞き返す力の絞り方は revisit-4（いまの話を聞き切る）
- validate-3（結果で見立てを変えない）: アプリは、出来事の結果の良し悪しや、結果を話したかどうかで見立てを変えない
- validate-4（根拠は本人の言葉）: アプリは、「根拠あり」と「要確認」の力に、根拠として本人が書いた言葉を一字一句そのまま引いて添える。選択肢を選んだ答えを根拠に使うときは、選んだ答えだと分かるように示し、結びついた本人の言葉と並べる（示し方は Claude の判断）
- validate-5（選んだだけでは根拠にしない）: もし利用者が選択肢を選んだだけで、本人が話したほかの事実と結びついていなければ、アプリはそれを根拠にしない
- validate-6（否定の言葉を使わない）: アプリは「根拠なし」「不得意」「まだ強みとは言えません」のような言い方をしない。点数や順位も出さない
- validate-7（見えた力と、もう少し聞きたいことを示す）: エピソードを話し終えたとき、アプリは、この話から見えた力と根拠、もう少し聞かせてほしいことを示す。見せ方は [4-rules.md](4-rules.md) の「画面での見せ方」。状態の呼び名や核となる行動のチェック表は、画面の前面に出さない（Claude の判断）
- validate-8（訂正したら確かめ直す）: 利用者が自分の発言や AI の読み取りを訂正したとき、アプリは確かめ直し、いつ、何が、なぜ変わったかを履歴に残す
- validate-9（生活での根拠と仕事での発揮を分ける）: アプリは、生活の中で確かめたことと、仕事でも発揮できそうかを、別々に記録して示す。ハッカソンの期間中は、仕事での発揮はいつも「まだ確かめていない」と示す
- validate-10（一般論には具体的な出来事を聞く）: もし利用者の話が一般論だけで、具体的な出来事がなければ、アプリは「要確認」とし、具体的な出来事を一つ聞く
- validate-11（要確認の場面に戻れる）: 「要確認」のまま終わった場面があるとき、アプリは、利用者がその場面に戻って続きを話せるようにする（Claude の判断）
- validate-12（本人が見立てを外せる）: 利用者が力の見立てを外したいとき、アプリはその力を、カードの理由と可能性レポートから外す。外したことは履歴に残す

## 04 profile（5 つの記録）

5 つの記録の意味は [5-information.md](5-information.md)。

- profile-1（5 つを分けて残す）: アプリは、できること、好み、やりたいこと、条件、主体性を、混ぜずに別々に記録する
- profile-2（できることは根拠とつなぐ）: アプリは、「できること」に、「根拠あり」の力とその根拠を入れる。「要確認」の力は「確かめ中」として分けて示す
- profile-3（条件を先に聞く）: 仕事の選択肢を出す前に、アプリは使える時間帯、週あたりの時間、在宅か外出できるか、収入の目安を聞く
- profile-4（本人が直せる）: アプリは、利用者が 5 つの記録のどれでも直せるようにする。P1 で AI が会話から推し量って書く項目を足すときは、推し量ったものだと分かるように示す（Claude の判断）
- profile-5（好みとやりたいことを一つずつ聞く）: 仕事の選択肢を出す前に、アプリは好みとやりたいことを、選択肢つきの問いで一つずつ聞く（Claude の判断）
- profile-6（主体性は本人が書く）: アプリは、主体性を推し量らず、本人が書く欄だけを置く

## 05 options（仕事の選択肢）

カードの決まりは [4-rules.md](4-rules.md)。

- options-1（3 枚を同じ重さで示す）: 条件がそろったとき、アプリは「選ぶ」「組み合わせる」「創る」の 3 枚のカードを同じ重さで示す。順位を付けない
- options-2（選ぶは登録した職種から）: アプリは、「選ぶ」のカードを、登録した実在の職種と業務のデータからだけ出す。AI が職種を作らない
- options-3（組み合わせるは登録した業務から）: アプリは、「組み合わせる」のカードを、登録した業務を 2〜3 個組み合わせて作る。AI が書くのは、役割の名前と、本人の力に合う理由だけ
- options-4（創るは根拠を引けるときだけ）: もし本人の根拠を引けなければ、アプリは「創る」のカードを出さない。出すときは「事業のアイデアで、需要はまだ確かめていない」と必ず示す
- options-5（条件の範囲だけ）: アプリは、本人の時間と場所の条件の範囲で成り立つカードだけを出す。収入は、本人の目安と比べて示す。「創る」は需要をまだ確かめていないので、収入の数字は示さない（Claude の判断）
- options-6（本人が選ぶ、保留する、自分で書く）: アプリは、利用者がカードを一つ選ぶ、決めずに保留する、自分で考えた仕事を書く、のどれでもできるようにする。本人の希望と AI の案が違うときは、両方を残す
- options-7（1 場面で進める）: 利用者が一つの場面を話し終え、条件を入れたとき、アプリは仕事の選択肢へ進めるようにする。「根拠あり」の力がなければ、「要確認」の力を「確かめ中」と示して使う

## 06 deepen（選んだ案を深める）

- deepen-1（選んだ 1 案だけ深める）: 利用者が案を一つ選んだとき（本人が書いた仕事を含む）、アプリはその案だけを深める。選ばなかった案は深めない
- deepen-2（業務ごとに照らす）: アプリは、選んだ案の業務ごとに、確かめた力と根拠が使えるところと、まだ確かめていないことを示す。「選ぶ」と「組み合わせる」は登録した業務を使う。「創る」と本人が書いた仕事は、AI が業務を見立てとして書き、本人が直せるようにする。登録した職種のようには見せない（Claude の判断）
- deepen-3（最初の一歩は小さく）: アプリは、条件の範囲でできて、失敗しても負担の小さい最初の一歩の候補を 3 つ示す（数は Claude の判断）。利用者は、候補から選んでも自分で書いてもよく、1 つでも複数でもよい
- deepen-4（創るの一歩には需要の確かめを入れる）: 選んだ案が「創る」のとき、アプリは最初の一歩に、知人数人に聞くような小さな需要の確かめを含める
- deepen-5（うまくいかなくても次へ）: アプリは、一歩がうまくいかなかったときの受け止め方（「力がない」ではなく「仮説を確かめた結果」）と、次の案の考え方を添える
- deepen-6（仮の場面での考え方を聞く）: 利用者が案を一つ選んだとき、アプリは、その案の仕事の場面で、仮の状況ならどうするかを 1〜2 問聞く（数は Claude の判断）。答え方は経験の問いと同じく、選択肢 3 つと「それ以外」、自由に書く欄にする。答えは考え方の傾向として残して示し、それだけで力の状態を上げない

## 07 report（可能性レポート）

- report-1（一つにまとめて示す）: 利用者がレポートを開いたとき、アプリは確かめた力と根拠、まだ確かめていないこと、5 つの記録、選んだ案、仕事の場面での考え方の傾向、最初の一歩をまとめて示す
- report-2（直す、保留する、次の一歩を選ぶ）: アプリは、利用者がレポートから、内容を直す、決めずに保留する、次の一歩を選ぶか書く、のどれでもできるようにする
- report-3（版を残す）: レポートの内容が変わったとき、アプリは前の版を残し、いつ何が変わったかを分かるようにする
- report-4（決めつけない）: アプリは「あなたに向いている仕事は〜です」のような言い方をせず、本人が選んだこととして書く
- report-5（保留しても開ける）: 利用者が案を選ばずに保留していても、アプリは可能性レポートを開けるようにする
- report-6（話を足したら作り直す）: レポートのあとに利用者がまた話したとき、アプリはカードとレポートを作り直し、レポートの版を一つ増やす

## 08 revisit（別の日に話す）

一つの話で力を言い切らず、別の日にまた話せるようにする。力を確かめる物差しは変えない。決まりは [4-rules.md](4-rules.md) の「話の数」「別の日の入口」「カレンダーに入れる」。足すと決めたのは開発者で、線引きと言葉は Claude の判断。当事者の協力者に確かめている途中（[README.md](README.md) の「決めていないこと」）。

作るときは、02 discover（話す）、03 validate（確かめる）、04 profile（5 つの記録）、07 report（可能性レポート）の Spec と、`docs/specs/00-common.md` の「次にできること」も合わせて直す。

- revisit-1（話の数に合わせて言う）: アプリは、根拠ありの力に、確かめられた話の数を添えて示す。話が 1 つなら「1 つの話から見えた力」、2 つ以上なら「2 つの話に出てきた力」のように言う。見えた力の画面、5 つの記録の「できること」、可能性レポートで同じ言い方にする
- revisit-2（別の話の根拠を積み上げる）: 別の話でも同じ力の核となる行動がすべてそろったとき、アプリは話の数を増やし、前の話の根拠を残したまま、新しい話の根拠を並べる
- revisit-3（別の日の入口を用意する）: 話し終えた場面がある人が、前に話した日とは別の日に新しい場面を始めるとき、アプリは、決めた一歩があり、その後をまだ聞いていなければ、そのことを一つ聞く。なければ、最初の問いに「また」を添えて聞く
- revisit-4（いまの話を聞き切る）: 場面を話している間、アプリは、いま話している出来事から話を移さず、足りない行動を聞き返す力を一つに絞る。ほかの力は、本人の話に出てきたら拾うが、追いかけて聞かない
- revisit-5（また話せると一言添える）: 一歩を決めたときと可能性レポートで、アプリは別の日にまた話せることを一言添える。期限や約束は求めない。いま次にすることがない人が別の日にホームを開いたときは、次にできることとして「話す」を示す
- revisit-6（話さなくても何も変わらない）: もし利用者がまた話さなくても、アプリは力の見立て、カード、レポートを変えない。「あと何回」「足りない」「まだ 1 つだけ」と言わず、話の数で何かが開く仕組みにしない
- revisit-7（つらい話を持ち出さない）: もし、いちばん新しい話がつらい状態のサインに応えたところで終わっていたら、アプリは入口で一歩のその後も前の話も持ち出さず、いつもの問いで始める（気持ちが動いた日ではなく、ふだんの一日を聞く）。また話せるという一言も、カレンダーに入れる操作も出さない。飛ばした話と、本人が外した力にもふれない
- revisit-8（本人が選んだときだけカレンダーに入れる）: 一歩を決めたときと可能性レポートで、アプリは「また話せる」の一言のそばに、別の日をカレンダーに入れる操作を置く。利用者が日を選んだとき、アプリは予定の下書きを本人のカレンダーに渡す。保存するのは本人で、アプリはカレンダーの権限を求めない
- revisit-9（予定に話の中身を書かない）: アプリは、予定に決まった言葉とアプリの URL だけを書く。話した内容、一歩、力、仕事の案は書かない
- revisit-10（入れたかどうかを持たない）: アプリは、カレンダーに入れたかどうかも、選んだ日も、保存せず数えない。予定の日に開かなくても何も言わない
